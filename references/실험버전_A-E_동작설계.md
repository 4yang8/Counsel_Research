# 내담자 에이전트 실험 버전 A~E 동작 설계

## 문서의 범위

QA.md와 QA2.md, 이후 논의한 내용을 바탕으로 각 실험 조건의 동작을 정리한다. A는 현재 `Q2a_trait_background`를 기준으로 하며, B~E는 아래 대응 버전으로 구현했다. 상세 실행 설정은 [구현 설명](../versions/memory_experiments/README.md)에 정리했다.

| 조건 | 구현 버전 |
|---|---|
| A | `Q2a_trait_background` (기준선 유지) |
| B | `Q2a_note_select` |
| C | `Q2a_note_retrieve` |
| D | `Q2a_turn_goal` |
| E | `Q2a_agentic_memory` |

- [QA.md](QA.md): 현재 상태와 변화 이력의 분리, 선택적 정보 제공, 원본 근거 조회.
- [QA2.md](QA2.md): 정보 충분성, 조회·종료 판단, 대화 의도와 내부 작업 목표의 구분.
- 기준선에는 최근 수정한 **글머리 항목별 노트 추가·수정·삭제 방식**을 포함한다. 실험 시작 시 코드·프롬프트·설정을 함께 고정한다.
- 이 문서는 구현 설계안이다. 각 방식의 효과나 인용 논문의 주장을 검증한 결과 보고서가 아니다.

## 1. 버전별 차이

| 조건 | 발화 생성에 처음 제공하는 노트 | 추가 조회 | 대화 의도와 표현 계획 |
|---|---|---|---|
| A. 현재 기준선 | 전체 현재 노트 | 없음 | 기존 `response_plan` 사용 |
| B. 노트 선택 | 라우터가 선택한 항목의 원문 | 없음 | A와 동일 |
| C. 노트 선택 + 능동 조회 | B와 동일 | 현재 노트·변경 이력·당시 원본 기록 | 기존 계획을 유지하되, 조회 결과에 따라 잠정 판단 수정 가능 |
| D. 대화 의도 명확화 | A처럼 전체 현재 노트 | 없음 | 이번 대화 의도와 표현 계획을 구분 |
| E. 통합 | B처럼 선택된 항목 | C와 동일 | D의 구분 + 근거에 따른 해석·의도·계획 재검토 |

B와 C는 A에서 출발하는 정보 제공 실험이다. D는 A에서 별도로 출발하는 의도 표현 실험이다. E는 C와 D를 결합한다.

## 2. 공통 동작과 용어

### 입력 정보

- 기본 프로필: 생활 배경, 현재 고민 등 기존에 기본 제공하던 정보.
- 공개 대화: 상담사와 내담자가 실제로 주고받은 발화.
- 이번 상담사 발화: 현재 반응해야 할 말.
- 관련 특성·배경: 기존 라우터가 선택하고 Python이 원문을 전달하는 개인 정보.
- 현재 내담자 노트: 현재 내면 3개 영역과 심리상태 10개 영역에 기록된 글머리 항목.

이번 비교에서 프로필 기본 제공 범위와 공개 대화 제공 범위는 유지한다. 대화히스토리 축약이나 상담사 가이드 변경은 별도 실험으로 둔다.

### 노트 관리

- 각 글머리 항목은 안정적인 ID를 가진다.
- 새로운 독립 내용은 추가하고, 같은 대상의 마음·조건이 달라지면 해당 항목을 수정한다.
- 해소·정정·중복으로 더 이상 유효하지 않은 항목은 삭제한다.
- 변경하지 않은 항목은 유지한다. 이번 입력에서 제외됐다는 이유로 저장된 노트를 삭제하지 않는다.
- 변경 근거와 삭제 전 내용은 실행 이력에 남긴다. 현재 노트에 모든 과거 과정을 다시 누적하지 않는다.
- 현재 노트에 근거·조건을 짧게 포함할 수 있지만, 상세한 변경 이력과는 구분한다.

### 발화 생성과 노트 갱신의 정보 범위

A~E 모두 **발화가 확정된 뒤 상태 검토·노트 갱신에는 전체 최신 노트를 제공**한다. B·C·E에서 노트를 선택적으로 제공하는 범위는 appraisal·반응 계획·발화 생성 단계다.

이렇게 해야 발화 생성에 필요한 정보 선택을 비교하면서도, 노트 갱신 시 보이지 않는 기존 항목을 중복 추가하는 문제를 줄일 수 있다. 확정된 공개 발화는 이후 노트 갱신 과정에서 바꾸지 않는다.

### 세 가지 서로 다른 판단

| 구분 | 질문 | 예시 |
|---|---|---|
| Appraisal | 상담사의 말을 나에게 어떤 의미로 받아들이고 무엇을 느끼는가? | 관심은 느껴지지만 바로 행동을 요구받는 것 같아 부담스럽다. |
| 대화 의도 | 이번 말에서 무엇을 표현하거나 지키려는가? | 도움받을 마음은 전하되 실행을 약속하지는 않고 싶다. |
| 표현 계획 | 그 의도를 어떤 말로 표현할 것인가? | 제안에 관심을 보이고, 준비할 시간이 필요하다고 말한다. |

에이전트의 내부 작업 목표는 이 셋과 구분한다. 예를 들어 “부담의 이유를 판단하기 위해 과거 appraisal을 확인한다”는 내부 작업이다.

## 3. A — 현재 기준선

### 목적

다른 조건의 비교 기준을 보존한다. 새로운 노트 선택·조회·대화 의도 필드를 추가하지 않는다.

### 실행 순서

1. 기존 특성·배경 라우터가 프로필 후보, 공개 대화, 이번 상담사 발화와 전체 현재 노트를 읽는다.
2. 라우터가 관련 특성·배경을 선택한다.
3. 메인은 기본 정보, 공개 대화, 이번 발화, 선택된 특성·배경과 **전체 현재 노트**를 받는다.
4. `stage_client_update`로 appraisal과 기존 `response_plan(action, reason)`을 기록한다.
5. `commit_client_utterance`로 공개 발화를 확정한다.
6. `select_client_states`로 검토할 심리상태 영역을 고른다.
7. `update_client_states`로 필요한 노트 항목만 추가·수정·삭제한다.
8. 모든 필수 기록이 완료되면 발화와 노트를 저장한다.

### 특징

메인은 처음부터 전체 현재 상태를 읽는다. 과거 기록은 저장되지만, 메인이 도구로 조회하는 기능은 없다. 현재 구현에서는 네 도구의 순서가 강제되어 있다.

## 4. B — 노트 선택

### 목적

현재 노트를 모두 제공하는 대신 관련 항목만 제공했을 때, 정보 활용과 반응의 일관성이 어떻게 달라지는지 확인한다.

### 실행 순서

1. 기존 특성·배경 라우터가 A와 같은 자료를 읽는다. 별도 라우터 에이전트를 추가하지 않는다.
2. 기존 출력에 **관련 노트 항목 ID 목록**을 추가한다.
3. Python이 선택된 특성·배경과 노트 항목의 원문을 전달한다. 노트를 요약하거나 새롭게 해석해 작성하지 않는다.
4. 메인은 선택된 노트로 appraisal·기존 반응 계획·공개 발화를 생성한다.
5. 발화 확정 후 전체 현재 노트를 다시 제공하고, A와 같은 상태 검토·항목 갱신을 수행한다.

### 정보 경계

- 선택되지 않은 노트는 저장 파일에 남아 있지만, 발화 생성 단계의 입력에서는 빠진다.
- 라우터는 항목의 관련성을 판단한다. 메인에게 전달할 노트 본문은 원문이다.
- 첫 턴처럼 노트가 비어 있으면 빈 선택으로 진행할 수 있다.
- B에는 추가 조회 기능이 없다. 선택 누락이 생겼을 때 메인이 어떻게 반응하는지도 관찰 대상이다.
- 빠진 항목의 본문이 다른 프롬프트나 도구 결과로 다시 들어가지 않도록 확인한다.

## 5. C — 노트 선택 + 능동 조회

### 목적

사전 선택만으로 부족한 경우, 메인이 필요한 현재 정보나 과거 근거를 찾아 판단을 보완하는지 확인한다.

### 조회 대상

| 대상 | 반환할 정보 | 확인하려는 것 |
|---|---|---|
| 현재 노트 | 관련 항목 ID·영역·현재 본문 | 처음 입력에서 빠진 현재 마음·조건 |
| 노트 변경 이력 | 턴·항목 ID·작업 종류·변경 전후 내용·변경 이유 | 무엇이 언제, 왜 달라졌는지 |
| 당시 원본 맥락 | 해당 턴의 상담사 발화·내담자 발화·appraisal·반응 계획 | 변경 요약의 의미와 근거를 원래 맥락에서 확인 |

현재 노트는 세션별 `state_notes.md`, 변경 이력과 원본 맥락은 세션의 턴별 기록을 활용한다. 초기 대상은 **동일 세션의 현재 기록과 완료된 과거 턴**이다. 다른 세션·미래 턴·진행 중 미확정 기록은 조회 범위에 넣지 않는다.

별도의 프로필 경험 검색이나 외부 웹 검색은 이 조건에 포함하지 않는다. 기존 특성·배경 라우팅은 유지한다.

### 실행 순서

1. B와 같이 관련 노트를 선택해 초기 입력을 만든다.
2. 메인이 잠정적으로 해석과 반응 방향을 검토한다.
3. 이번 반응의 중요한 판단에 부족한 근거가 있는지 확인한다.
4. 부족하다면 필요한 정보와 조회 이유를 지정해 도구를 호출한다.
5. 결과를 읽고 어떤 점이 확인됐는지, 판단을 바꿀 필요가 있는지 검토한다.
6. 새 단서 때문에 다른 근거가 필요하면 추가 조회하고, 충분하면 공개 발화를 확정한다.
7. 전체 현재 노트를 제공하고 상태 검토·노트 갱신을 수행한다.

조회는 appraisal을 처음 기록하기 전에도 필요할 수 있다. 발화 확정 전에는 조회 결과에 따라 잠정 appraisal·반응 계획을 다시 기록할 수 있어야 한다. 별도의 Turn Goal 필드는 C에 추가하지 않는다.

### 조회·종료 기준

- 조회: 반응의 해석·방향·공개 범위를 결정하는 데 중요한 근거가 부족하고, 조회 가능한 기록에서 확인할 가능성이 있을 때.
- 충분해서 종료: 중요한 판단에 필요한 근거가 확보되고 추가 조회로 해결할 구체적인 문제가 남지 않을 때.
- 자료 부족으로 종료: 필요한 기록이 없거나 추가 조회가 새로운 근거를 주지 못할 때. 충분해서 종료한 경우와 로그에서 구분한다.
- 실행 한도: 반복·과도한 조회를 막는 상한을 둔다. 횟수 등 수치는 구현 전에 정한다.

모든 턴에 조회를 강제하지 않는다. 기록을 찾지 못한 사실을 내담자의 기억 상실·거부감으로 바꾸지 않는다. 과거의 상태는 당시 시점의 기록으로 전달하며, 지금도 동일하다고 자동으로 간주하지 않는다.

## 6. D — 대화 의도 명확화

### 목적

정보 제공 방식을 바꾸지 않고, “무엇을 원하거나 지키려는가”와 “어떻게 표현할 것인가”를 구분하면 반응이 달라지는지 확인한다.

### 실행 순서

1. A와 동일하게 특성·배경을 라우팅하고 전체 현재 노트를 제공한다.
2. 이번 상담사 발화에 대한 appraisal을 생성한다.
3. 기존 `response_plan`의 내용을 다음 두 기능으로 명확히 구분한다.
   - 대화 의도: 이번에 표현하거나 유지하려는 바람·경계와 그 근거.
   - 표현 계획: 답할 내용, 보류할 내용, 표현 방식.
4. 그 의도와 계획을 바탕으로 공개 발화를 확정한다.
5. 전체 현재 노트로 상태 검토·갱신을 수행한다.

### 설계 범위

별도 목표 설정 에이전트나 검증 LLM을 필수로 추가하지 않는다. 같은 메인 호출에서 구분해 작성하는 방식으로 시작할 수 있다. 최종 필드 이름과 스키마는 구현 시 확정한다.

대화 의도는 매번 성과를 내거나 더 많이 공개하는 목표일 필요가 없다. 망설임 표현, 결정 보류, 오해 정정, 조건부 수용도 가능하다. 상충하는 마음과 불확실성을 유지할 수 있어야 한다.

대화 의도와 발화가 일치하는지만 보지 않고, **그 의도 자체가 개인 정보와 현재 경험에 타당한지** 함께 확인한다.

## 7. E — 선택적 정보·능동 조회·대화 의도의 통합

### 목적

C의 정보 탐색과 D의 대화 의도 구분을 결합했을 때, 필요한 작업을 선택하고 새로운 근거에 따라 반응을 조정하는지 확인한다.

### 실행 순서

1. 관련 특성·배경·노트 항목을 선택해 초기 입력을 만든다.
2. 메인이 잠정 appraisal과 대화 의도를 형성한다.
3. 그 판단에 부족한 정보나 중요한 모호함이 있는지 확인한다.
4. 필요한 경우 현재 노트·변경 이력·당시 원본 맥락을 조회한다.
5. 결과에 따라 해석·대화 의도·표현 계획을 유지하거나 수정한다.
6. 필요한 근거가 확보되면 계획에 맞는 발화를 확정한다.
7. 전체 현재 노트를 다시 제공해 상태를 검토하고 항목을 갱신한다.

### 동적 작업 선택의 의미

처음에 모든 작업을 정해 놓고 매번 수행하는 것이 아니다. 현재 판단에 무엇이 부족한지를 보고 조회·재검토·발화 확정 중 다음 작업을 고른다.

- 간단한 상황: 추가 조회 없이 발화 확정.
- 근거 부족: 필요한 과거 기록 조회 후 재판단.
- 새 근거와 잠정 판단의 충돌: appraisal이나 대화 의도부터 수정.
- 더 확인할 자료가 없음: 불확실성을 보존하고, 실행 한도와 종료 기준에 따라 종료.

복수 해석의 검토는 메인의 판단 안에서 수행할 수 있다. 이를 위한 별도 도구·서브에이전트나 항상 실행하는 생성 후 피드백 루프는 현재 설계에 포함하지 않는다.

## 8. 공통 상황으로 보는 차이

상담사 발화:

> 교수님께 다시 설명해보는 건 어떨까요?

현재 노트:

- 평가에 대한 걱정이 남아 있다.
- 다시 설명할 자신이 부족하다.
- 충분히 준비할 시간이 있다면 시도할 마음은 있다.
- 친구와의 갈등도 마음에 남아 있다.

과거 기록:

> 앞선 행동 제안을 들었을 때, 내담자는 준비할 여유 없이 바로 실행해야 한다고 받아들여 부담을 느꼈다. 자신의 걱정이 충분히 이해되기 전에 해결을 요구받는 느낌도 있었다.

| 조건 | 가능한 처리 예시 |
|---|---|
| A | 모든 현재 노트를 읽고 이번 제안에 대한 반응을 정한다. |
| B | 라우터가 평가 걱정·자신감·준비 시간에 관한 항목을 골라 주고, 메인은 그 정보로 반응한다. |
| C | 선택된 노트만으로 부담의 이유가 불분명하면 당시 기록을 조회한다. 즉시 실행 부담인지, 이해받지 못한다는 느낌인지 확인해 반응을 조정한다. |
| D | 전체 노트를 읽고 “시도할 마음은 전하되 바로 실행을 약속하지는 않겠다”는 의도와, 이를 표현할 계획을 구분한다. |
| E | 과거 근거를 확인한 뒤 의도를 “거절하기”에서 “준비 시간과 이해받고 싶은 마음을 설명하기”로 수정할 수 있다. 반대로 근거에 따라 보류를 유지할 수도 있다. |

이 예시는 동작 차이를 보여주기 위한 것이다. 특정 버전이 반드시 더 긍정적이거나 더 자기개방적인 발화를 만들어야 한다는 뜻은 아니다.

## 9. 공통 구현과 버전별 분기

| 공통으로 유지할 부분 | 조건별로 달라질 부분 |
|---|---|
| 프로필·대화·노트 저장 형식 | 초기 노트 전체 제공 / 선택 제공 |
| 글머리 항목 ID와 변경 적용·검증 | 라우터의 노트 ID 선택 출력 |
| 기본 appraisal와 발화 확정 기능 | 대화 의도와 표현 계획의 명시적 구분 |
| 발화 확정 후 상태 검토·노트 갱신 | 발화 확정 전 조회 및 판단 수정 허용 |
| 실행 로그·reasoning·노트 diff | 조회 이유·출처·판단 변화·종료 사유 기록 |
| 기본 UI | 버전별 설정 및 activation context 표시 |

현재 A의 도구 호출 순서는 강제되어 있다. C·E를 구현할 때는 도구 등록뿐 아니라 **발화 확정 전 조회·판단 수정이 가능하도록 실행 제약을 수정**해야 한다. 확정 이후에는 공개 발화를 소급 변경하지 않는다.

노트 선택은 메인 입력을 줄이지만, 라우터는 전체 노트를 읽고 상태 갱신 단계도 전체 노트를 읽는다. 따라서 전체 토큰 비용이 반드시 줄어드는 것은 아니다.

## 10. 관찰과 비교

| 비교 | 주로 확인할 차이 |
|---|---|
| A ↔ B | 관련 항목 선택의 효과와 중요한 항목 누락 |
| B ↔ C | 추가 조회가 누락 정보·과거 근거를 보완하는 효과 |
| A ↔ D | 의도와 표현 계획 구분의 효과 |
| C ↔ E | 조회가 있는 조건에서 의도 구분을 추가한 효과 |
| D ↔ E | 의도가 명시된 조건에서 선택적 정보 제공과 조회를 결합한 효과 |

D↔E는 정보 선택과 조회가 함께 달라진다. 이 비교만으로 두 요소의 개별 효과를 분리했다고 해석하지 않는다.

다음 사항을 함께 기록한다.

- 입력: 실제 제공·제외한 노트 항목 ID와 원문, 당시 프롬프트·모델·생성 설정.
- 조회: 부족하다고 판단한 정보, 대상·결과·시점·출처, 추가로 얻은 근거와 종료 사유.
- 판단: appraisal·계획·대화 의도의 변경 전후와 근거. 자연어 설명은 모델의 보고이며 그 자체로 인과 증명은 아니다.
- 결과: 발화의 맥락 적합성, 내면과 표현의 정합성, 이전 사실·상태의 왜곡 여부, 노트의 불필요한 증가.
- 비용: 메인과 라우터를 포함한 호출 수·입출력 토큰·지연. 조회 횟수가 많다는 이유만으로 높은 성능으로 판단하지 않는다.

같은 시작 프로필·노트·상담사 발화를 사용하는 한 턴 비교와, 이후 대화가 이어지는 연속 세션 비교를 구분한다. 연속 세션에서 상담사 모델도 응답하면 입력 경로가 달라지므로, 후반 결과 차이를 버전 변경 하나의 효과로 단정하지 않는다.

## 11. 구현 시 확정한 선택

- 실제 버전명은 문서 상단 표와 같고 UI에 A~E 조건을 함께 표시한다.
- 조회는 원문 단어 검색, 영역·항목 ID·턴 번호 필터, 페이지 범위를 지원한다.
- Python이 조건에 맞는 원문을 반환한다. 별도 요약 LLM은 추가하지 않았다. 긴 결과는 명시적으로 발췌 표시한다.
- `retrieve_client_memory` 하나의 current / changes / episodes 모드로 나눈다.
- 조회 최대 4회, 조회·잠정 판단 기록 합계 8회. 결과는 최대 5개·약 14,000자이며 반복 조회를 표시한다. evidence_decision에 충분·자료 부족·한도 종료를 구분한다.
- D·E는 turn_goal(intention / grounds / uncertainty)과 response_plan(action / reason)을 구분한다. C·E는 발화 확정 전 stage_client_update 재호출로 잠정 판단을 수정한다.

동작 및 기술 검증과 실제 모델의 효과 검증은 구분한다. 이번 구현은 별도의 평가 에이전트를 추가하지 않는다.
