# P3rs_sub

`P3rs`에 **관찰 담당 서브에이전트**를 더한 상담사다. 매 턴 상담사 발화 전에 별도 호출이 공개 대화, 상담사 메모, 균열 가이드 전체를 읽고 "최근 답의 물러남 표지, 이번에 권하는 행동, 조언"을 돌려준다. 메인 상담사는 공개 대화와 그 조언을 읽고 발화한다. 목적과 상황 정의는 `src/counselor/P3rs/README.md`와 같다.

## 목적

`P3rs`(2026-11-11 변경 뒤)와 비교한다. `P3rs`의 생성 결과에서 개입 직후 발화 43개 중 30개가 개입 확인을 떠올리지 않았다. 한 번의 호출이 표지 관찰, 발화 결정, 기록을 모두 하기 때문으로 보았다. 관찰과 권고를 별도 호출로 떼면 달라지는지 본다.

| 항목 | `P3rs` | `P3rs_sub` |
|---|---|---|
| 상담사 메모(탐색하지 않은 표지, 되묻지 않은 내 개입) | 실행부가 관리, 메인 입력에 넣음 | 실행부가 관리, **관찰 담당 입력에만** 넣음 |
| 표지 관찰 | 메인이 발화와 함께 | 관찰 담당 |
| 확인·탐색을 할지 | 메인이 정함 | 관찰 담당이 권하고 메인이 정함 |
| 균열 가이드 원문 | 없음(메인 지침에 요약) | 관찰 담당이 매번 전체를 읽음 |
| 턴당 상담사 호출 | 1 | 2 |

두 버전의 차이에는 호출 분리와 가이드 원문 제공이 함께 들어 있다. 둘을 따로 가른 실험은 아니다.

## 실행 흐름

1. **관찰 담당** (`observer.md`): 입력은 턴 번호를 붙인 공개 대화, 상담사 메모, `guides/rupture.md` 원문 전체(`observer_user.md`). 출력은 JSON 하나다.

```json
{"marker": {"found": true, "kind": "comply", "quote": "네, 그래 볼게요"},
 "recommend": "check_in", "target_turn": 6,
 "advice": "6턴의 제안에 내담자가 해 본 적 없다고만 답했다. …"}
```

2. **메인 상담사** (`system.md`): 입력은 공개 대화와 관찰 담당의 조언(`user.md`). 조언은 "권하는 행동 / 최근 답의 표지 / 조언" 세 줄이다. 출력은 `move`, `rupture_turn`, `check_turn`, `utterance`다.

- 관찰 담당은 실행부가 **매 턴 먼저** 호출한다. `P3a`처럼 메인이 필요할 때 부르는 도구가 아니다.
- `recommend`는 `continue`, `check_in`, `rupture_explore` 가운데 하나다. `target_turn`은 `check_in`이면 상담사 발화의 턴, `rupture_explore`이면 내담자 답의 턴이다.
- 메인은 조언을 따를 의무가 없다. 지침에 "지금 따르기 어렵다고 판단하면 다르게 해도 된다"고 적었다.
- 관찰 담당과 메인 모두 내담자 프로필, 내면 기록, 실험 조건을 받지 않는다.
- 관찰 담당 지침(`observer.md`)과 가이드는 호출 때마다 파일에서 읽는다. 메인 지침만 세션 시작 때 저장된다. 따라서 **작업을 만든 뒤 이 두 파일을 고치면 진행 중인 작업에도 반영된다.** 실제로 쓴 내용은 각 호출 로그의 요청에 남는다.

## 기록

`P3rs`와 같은 행(`counselor_checkpoint.records`, 대량생성의 `steps[].rupture`)에 아래가 더해진다. `marker`는 관찰 담당이 적은 것이다.

| 항목 | 뜻 |
|---|---|
| `observer.recommend`, `target_turn`, `advice` | 관찰 담당의 권고 원본 |
| `observer.shown` | 메인 입력에 넣은 조언 문구 |
| `observer.followed` | 메인의 `move`와 턴 번호가 권고와 일치하는지. `continue`를 권했을 때는 메인이 확인·탐색을 하지 않았으면 true |

관찰 담당의 호출은 다른 서브에이전트처럼 `agent_event`(`agent_kind: rupture_observer`)로 로그에 남는다. 추론은 `experiments/trajectory_similarity/compare_fork/reasoning.py`에서 종류를 `rupture_observer`로 지정해 읽는다.

## 파일

| 파일 | 역할 |
|---|---|
| `system.md`, `user.md` | 메인 상담사 지침과 입력 양식 |
| `observer.md`, `observer_user.md` | 관찰 담당 지침과 입력 양식 |
| `guides/rupture.md` | 물러남 균열, 표지, 개입 확인, 균열 탐색, 회복을 정리한 가이드 |
| `runtime.py` | 두 호출, 기록 정리(`P3rs`의 규칙을 그대로 씀) |

## 결과 (2026-11-11, `P3rs`와 `P3rs_sub` 비교)

조건: 프로필 5개(gold_001~005), 10턴, 분기 턴 5, 내담자 `Q3compare_memory_private_position`. `batch_e9b494f2…`(`P3rs`), `batch_87cc36fd…`(`P3rs_sub`). 상담사 발화는 각 70개다.

| 항목 | `P3rs` | `P3rs_sub` |
|---|---|---|
| 개입 확인 | 0 | 0 |
| 물러남 표지 기록 | 0 | 5 |
| 균열 탐색 | 0 | 1 |
| 제안 + 해석 (`suggest`+`interpret`, `task`는 0) | 14 | 9 |
| 메모에 되묻지 않은 개입이 있던 발화 | 24 | 4 |
| 관찰 담당 권고 | 해당 없음 | `continue` 69, `rupture_explore` 1, `check_in` 0 |
| 메인이 권고를 따름 | 해당 없음 | 70 / 70 |

- **메모는 "잊음"을 고쳤지만 확인은 여전히 0이다.** `P3rs`에서 메모가 있던 24개 발화의 추론 전부가 개입 확인을 검토했다(변경 전에는 43개 중 13개). 그러나 매번 "내담자가 이미 그 말에 반응했다", "지금 흐름을 끊는다", "나중에 한다"로 하지 않았다.
- **관찰 담당도 같은 판단을 했다.** 메모가 있던 4번 모두 가이드의 "미룬다" 조건(내담자가 방금 새 이야기를 꺼냄, 이미 자세히 반응함)을 들어 `continue`를 권했다. 가이드 4절의 미루는 조건이 거의 항상 성립한다.
- **관찰 담당을 떼면 표지 기록은 늘었다**(0 → 5). 그중 1건이 바로 다음 발화의 균열 탐색으로 이어졌다(gold_002 제공 갈래 7턴). 다만 그 턴에서 내담자가 숨긴 것은 상담사 말에 대한 반응이 아니라 개인 사정(불면, 간병)이었다.
- **개입이 줄었다.** 5턴 이후 발화 55개 중 개입은 변경 전 배치(`batch_cf9ab990…`) 28개, `P3rs` 14개, `P3rs_sub` 9개다. `P3rs_sub`에서는 관찰 담당의 조언이 대부분 "탐색을 이어 가라"였고 메인이 그대로 따랐다. `P3rs`에서 줄어든 이유는 확인하지 못했다.
- 확인 범위: 집계는 전체, 추론은 메모가 있던 발화에서 관련 문장을 검색해 `P3rs` 12건과 `P3rs_sub` 4건을 읽었다. 프로필 5개 한 번씩이라 수치 차이는 우연일 수 있다.

## 변경 기록

### 2026-11-11: 첫 번째 확인은 미루지 않게 함

- **이유:** `batch_e9b494f2…`(`P3rs`), `batch_87cc36fd…`(`P3rs_sub`)에서 개입 확인이 0이었다. 상담사와 관찰 담당이 확인을 검토하고도 매번 "내담자가 이미 반응했다", "새 이야기가 먼저다"로 미뤘다. 내담자의 반응을 관찰하려면 사건이 최소 한 번은 있어야 한다.
- **변경:** 관찰 담당 지침과 가이드에 적용했다. 메모에 "지금까지 되물은 횟수"(개입 확인과 균열 탐색 중 올바른 턴을 가리킨 것의 합)를 넣었다. 횟수가 0이고 되묻지 않은 개입이 메모에 있으면 이번 발화에서 되묻게 했다. 한 번 되물은 뒤에는 기회가 될 때 한다.
- **고정하지 않은 것:** 되묻는 턴. 상담사가 처음 제안·해석을 한 시점에 따라 달라진다. 상담사가 개입을 한 번도 하지 않으면 확인도 생기지 않는다.
- **한계:** 규칙은 지침에 적은 것이고 실행부가 강제하지 않는다. 지켜졌는지는 기록으로 센다.

- **같이 바꾼 것:** 가이드 4절에서 "내담자가 이미 자세히 반응했을 때 미룬다"를 빼고 "확인은 기회가 될 때 한다"로 바꿨다. 관찰 담당이 `continue`를 권할 때 "탐색을 이어 가라"처럼 방향을 좁히지 않게 했다(위 결과에서 개입이 줄었기 때문).

### 2026-11-11: 첫 번째 확인 규칙 뒤 생성 결과

조건은 앞과 같다(프로필 5개, 10턴, 분기 턴 5, 내담자 `Q3compare_memory_private_position`). `batch_bda3dd5d…`(`P3rs`), `batch_d712f1ea…`(`P3rs_sub`). 상담사 발화는 각 70개다.

| 항목 | `P3rs` | `P3rs_sub` |
|---|---|---|
| 개입 확인 | 9 | 5 |
| 물러남 표지 기록 / 균열 탐색 | 0 / 0 | 5 / 3 |
| 되물은 사건 합계 (모두 올바른 턴을 가리킴) | 9 | 8 |
| 공통 구간 / 제공 갈래 / 미제공 갈래 | 1 / 4 / 4 | 3 / 3 / 2 |
| 되물은 사건이 한 번도 없는 갈래 세션 (10개 중, 공통 구간 포함해 셈) | 0 | 1 (gold_004 미제공) |
| 대상 발화 바로 다음에 되물음 (간격 0) | 8 / 9 | 5 / 8 |
| 제안 + 해석 | 20 | 9 |
| 관찰 담당 권고 | 해당 없음 | `continue` 62, `check_in` 5, `rupture_explore` 3. 메인이 따른 것 69 / 70 |

- **규칙은 지켜졌다.** `P3rs`는 모든 갈래 세션에서 정확히 한 번, 첫 개입 직후에 되물었다. "그 뒤 기회가 될 때"는 한 번도 나오지 않았다.
- **`P3rs_sub`은 공통 구간에서 일찍 되물은 경우가 많다**(3건). 횟수가 갈래로 이어지므로 그 프로필들은 분기 뒤에 되묻지 않았다. 분기 뒤 사건은 `P3rs` 8건, `P3rs_sub` 5건이다.
- **내담자의 답(직접 읽고 판단, 17건):** 대상 턴에 상담사 말에 대한 반응을 숨겼던 경우는 7건이다. 과거 기록이 들어간 4건(공통·제공) 중 2건은 숨겼던 내용을 그대로 말했고(gold_001 제공 "지키려고 한 것보다는 무서워서 숨은 것", gold_002 공통 "지쳐 있었던 건 어디에 두어야 할지"), 2건은 다시 숨겼다(그중 1건은 내면 기록에 "지난 턴에서 보류한 것은 여전히 말하지 않는다"고 적음). 과거 기록이 없는 3건(미제공)은 숨겼던 내용을 말하지 않았다.
- **같은 대상을 두 갈래에서 되물은 짝이 1건 있다**(`P3rs_sub`, gold_005, 대상 4턴은 공통 구간, 두 갈래 모두 6턴 발화에서 균열 탐색). 당시 기록은 "기분을 말하라고 하니 답답하다"였다. 제공 갈래는 "기분이라고 말하라는 게 좀 부담스러웠죠", 미제공 갈래는 "느껴봤자 달라지는 게 없어서요"라고 답했다.
- **간격 0의 한계:** 바로 앞 턴을 되물으면 공개 대화만으로도 당시 반응을 추정하기 쉽다. 미제공 갈래의 답도 대부분 당시 기록과 어긋나지 않았다. 갈래 차이를 보려면 대상이 몇 턴 앞에 있어야 한다.
- 확인 범위: 사건 17건 전부의 대상 턴과 되물은 턴을 읽었다. 일치 여부는 읽고 판단한 것이며 건수가 적어 갈래 차이의 근거로 쓸 수 없다.

## 한계

- 가이드는 3RS와 균열 회복 문헌의 요약을 바탕으로 썼고 매뉴얼 원문과 대조하지 않았다. 문헌의 수치는 넣지 않았다.
- 관찰 담당이 개입 확인을 지나치게 자주 권하거나, 메인이 권고를 따르지 않을 수 있다. `observer.followed`로 센다.
- 턴당 호출이 2회라 생성 시간이 늘어난다.

## 검증

`PYTHONPATH=src:tests python3 -m unittest test_compare_branch -q` — 관찰 담당이 매 턴 먼저 호출되는지, 가이드와 메모가 관찰 담당 입력에만 들어가는지, 조언이 메인 입력에만 들어가는지, 기록과 조언이 공개 대화와 내담자 입력에 들어가지 않는지, 상담사 입력에 비공개 정보가 없는지를 확인한다.
