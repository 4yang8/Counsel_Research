# P3rs 상담사 실험군

목적은 일반적인 상담사 능력 최적화가 아니라 **맥락에 맞는 제안·해석 → 내담자 반응 → 그 순간에 대한 후속 확인**이 자연스럽게 발생하는 구조를 비교하는 것이다. 비공개 반응, 지연 공개, 제공 조건의 우위를 강제하지 않는다. 모든 상담사 입력은 공개 대화와 자기 기록만 사용한다.

기존 `P3rs`와 `P3rs_sub`는 기준점으로 보존했다. 새 8개는 각 버전 폴더의 프롬프트와 `rs_variants/runtime.py`의 서로 다른 실행 경로를 사용한다. 새 버전은 배치 생성 시 시스템/보조 프롬프트와 user 템플릿을 `rs_prompt_bundle`로 고정한다. 공통 세션에서 분기할 때 상담사 상태와 이 묶음도 복제된다. 원래 두 버전의 기존 프롬프트 로딩 정책은 바꾸지 않았다.

## 구조와 비용

발화 1개당 정상 실행 기준. LLM 호출은 토큰 수가 아니라 요청 수다. 수정은 최대 1회. 오류 재시도는 배치 설정에 따로 기록된다.

| 버전 | 실행 경로 | 보조 호출 수 | 전체 LLM 호출 | 실제 function tool 호출 | 메모 접근/변경 |
|---|---|---:|---:|---:|---|
| P3rs | 기존 단일 판단·발화 | 0 | 1 | 0 | 메인 읽기, 코드 갱신 |
| P3rs_sub | 기존 관찰·권고 → 메인 | 1 | 2 | 0 | 관찰 담당 읽기, 코드 갱신 |
| P3rs_sub_gate | 관찰 → continue 조언 차단 → 메인 | 1 | 2 | 0 | 관찰 담당 읽기, 코드 갱신 |
| P3rs_observe | 행동을 권하지 않는 관찰 → 메인 | 1 | 2 | 0 | 관찰 담당 읽기, 메인은 관찰 출력만 |
| P3rs_ledger | 사건 갱신 → 메인 | 1 | 2 | 0 | 이전 사건 → 변경안 적용 → 메인에 전달 |
| P3rs_tools | 자율 조회/수정 → 발화 확정 | 0 | 1~4 | 1~4 | 선택 도구 0~3회; 사건 수정 최대 1회 |
| P3rs_dual | 개입 후보 ∥ 확인 후보 → 메인 | 2 | 3 | 0 | 두 후보 담당이 같은 이전 메모를 독립적으로 읽음 |
| P3rs_hypothesis | 대안 해석 갱신 → 메인 | 1 | 2 | 0 | 이전 사건·해석 → 갱신된 해석을 메인에 전달 |
| P3rs_review | 초안 → 검토 → 선택적 수정 | 1 | 2~3 | 0 | 메인 메모, 검토에는 최근 행동 요약만 전달 |
| P3rs_full | 사건 갱신 → 두 후보 병렬 → 초안 → 검토 → 선택적 수정 | 4 | 5~6 | 0 | 갱신 담당→두 후보→메인, 검토는 관련 사건 참조 |

`P3rs_tools`의 1~4회에는 마지막 `finish_counselor_utterance`가 포함된다. 선택 도구는 `list_open_events`, `read_public_turns`, `update_event`. 메모 쓰기는 실행 중 임시 상태에만 적용하고 최종 발화가 성공해야 checkpoint에 반영한다. 함수 도구가 아닌 버전도 파이프라인 코드가 파일을 저장한다. 모든 버전은 성공한 상담사 턴마다 checkpoint를 한 번 확정한다.

## 각 비교의 의미

- gate: 기존 sub에서 continue일 때 자유 조언뿐 아니라 관찰 표지를 메인에 별도 전달하지 않고, 자기 상담을 진행하도록 한다. 원문 observer 결과는 기록에 남는다. 이 handoff 차이를 평가 시 명시한다.
- observe: 추천 행동/대상/조언 필드 자체가 없는 관찰 스키마. 메인이 행동을 결정한다.
- ledger: 자기 제안·해석·과제 사건의 원문은 불변. 공개 후속 반응/미확인점/상태만 근거 인용으로 갱신한다. 질문한 시점은 `asked`이며 해결/답변 완료로 자동 처리하지 않는다.
- dual: 두 보조 담당을 ThreadPoolExecutor로 병렬 호출한다. 서로의 출력을 보지 않으며, 메인이 둘 중 하나 또는 다른 행동을 선택한다. 후보를 둘 다 말하도록 강제하지 않는다.
- hypothesis: 공개 반응에 가능한 해석과 각각의 지지/반대 근거를 유지한다. 숨은 마음의 정답이나 수치 확률을 만들지 않는다.
- review: 행동·대상과 발화의 일치, 유도·반복·경계 무시만 검토한다. 일반 상담 스타일을 더 무난하게 만드는 검토가 아니다.
- full: 위 기능을 조합한 복잡한 후보이며 좋은 결과를 보장하는 버전이 아니다.

## 기록과 원자성

`session.json → counselor_checkpoint`:

- `records`: 기존 P3rs 호환 `marker/move/check/explore` + `pipeline`.
- `pipeline.stages`: 단계별 실제 입력/구조화 출력. tools에서는 도구 인자·결과와 요청 입력.
- `pipeline.llm_calls/tool_calls/agent_usage`: 호출 수와 사용량.
- `pending/unchecked`: 기존 표지/미확인 발언 목록.
- `events`: 사건 원문, 공개 반응, 확인 상태, 근거 인용.
- `hypotheses`: 가능한 해석과 지지/반대 근거.
- `prompt_bundle`: 사용한 보조 지침과 템플릿.

후보·검토·수정은 공개 대화에 추가되지 않는다. raw 요청·응답·reasoning은 기존 `events.jsonl`에 agent_event로 남는다. 검토 입력에는 과거 pipeline 전체를 재귀적으로 넣지 않고 최근 행동의 필수 필드만 전달한다. 실패한 턴의 임시 메모는 checkpoint에 확정하지 않는다. 취소는 각 단계/스트림에서 확인한다.

## 한계

정확한 턴/인용·자료형은 코드로 검증하지만, 관찰·상태·행동의 의미적 적합성은 모델 판단이다. 한 번 이상 확인하라는 것은 공통 프롬프트 지침이며 코드가 특정 턴에 질문을 강제하지 않는다. 실제 상담 상황의 발생과 자연스러움은 새 생성 후 별도로 평가해야 한다.
