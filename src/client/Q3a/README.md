# Q3a · 턴별 로컬 플래닝

Q3를 복제한 비교 버전. 기본 입력·특성/배경/노트 라우터·사전 신뢰 궤적·조회 대상·발화 후 기록은 유지하고, 메인 모델의 **계획 → 수행 → 결과 확인 → 필요 시 재계획**을 명시적 도구 루프로 추가한다. 별도 계획 에이전트는 만들지 않는다.

## 작업 계획과 반응 계획의 구분

- 로컬 작업 계획의 `goal`: 이번 발화가 충족할 생성 목표. `steps`: 그 목표를 위해 해결할 판단·근거 확인, 완료 기준, 상태, 결과, 출처.
- `turn_goal`: 내담자 본인이 이번 말로 표현하거나 지키려는 바람·경계.
- `response_plan`: 실제로 무엇을 어떻게 말하고 보류할지.
- 내담자 노트: 다음 반응에 이어 줄 현재 마음. 사전 궤적: 전체 변화 방향. 진행 기록: 현재 마음과 궤적의 관계.

계획 단계는 발화 전 판단·조회 범위다. 최종 내면 판단 기록·발화 확정·노트 갱신은 계획을 마친 후 공통 절차로 이어진다. 모델이 단계 종류와 순서를 선택하며, 이미 주어진 정보를 비교·해석하는 작업도 수행으로 인정한다. 도구 사용을 만들기 위해 자료를 숨기지 않는다.

## 실행

1. 기존 라우터가 관련 특성·배경·노트 원문을 선택한다.
2. 메인의 첫 호출은 `update_turn_plan`: goal, 구체적인 task와 completion_criterion을 가진 대기 단계들을 등록한다.
3. 같은 도구의 `start`로 한 단계를 시작한다. 입력을 분석하거나, 필요하면 `retrieve_client_memory`로 기록을 조회한다.
4. `complete`로 실제 판단 결과·근거를 남긴다. 필요하면 `revise`로 다시 검토하거나 `skip`·`add`로 계획을 바꾼다. 다음 단계가 정해지면 완료와 다음 단계 시작을 한 요청에 묶고, 실행 결과를 확인해야 다음 단계를 정할 수 있으면 분리한다.
5. 모든 단계가 완료/생략이고 적어도 하나가 완료되면 `stage_client_update`로 결과를 종합한다. 재계획하면 이를 다시 수행해야 발화를 확정할 수 있다.
6. `commit_client_utterance` → 전체 내담자 노트 복원 → `update_client_notes` → `update_trajectory_progress`.
7. 모든 기록에 성공하면 발화·노트·진행·로컬 계획 이력을 함께 저장한다. 실패 시 완료 기록과 심리 노트는 갱신하지 않으며 실패한 시도의 이벤트는 실행 로그에서 조회한다.

도구의 간소한 처리 결과(`accepted`, `revision`, 단계 ID별 상태 `steps`, `ready_for_judgment`, `remaining_plan_updates`)가 다음 모델 호출의 `role:tool`에 들어간다. 목표·작업·수행 결과·근거는 성공한 호출 인자에서 참고하며, 전체 계획을 매번 반환하지 않는다. 전체 계획과 이력은 기존 version event와 완료 기록에 보존하여 UI에서 조회한다. 같은 턴의 reasoning·도구 호출·결과는 계속 유지한다. 계획 완료 표시를 Python이 의미상 검증하는 것은 아니다. Python은 상태 전이·필수 결과·출처 형식·도구 사용 단계만 검사하며, 결과가 실제 자료로 뒷받침되는지는 모델의 수행 품질로 평가해야 한다.

## 저장과 UI

- `appraisals/<turn>_<id>.json`의 `local_plan`: 최종 계획, `local_plan_history`: 변경 요청·당시 계획·조회 시점. 심리 노트와 분리된 작업 기록이다. 별도 중복 최신 파일 없이 이 원본을 UI에 표시한다.
- 다음 턴 메인·라우터에는 이전 로컬 계획을 자동 주입하지 않는다. 턴별로 빈 작업 계획에서 시작한다.
- 실험 설정 → 내담자 버전에서 Q3a 선택. 메인/라우터 system·user 템플릿, 사전 궤적을 독립적으로 편집한다.
- 생성 과정의 상세 기록: 작업 목표와 대기/진행/완료/생략 체크리스트, 결과·근거 표시.
- 결과의 노트 탭: 마지막 완료 턴의 계획을 심리 노트·궤적과 별도 박스로 표시.
- 내담자 노트 탭: 턴별 계획 조회, ‘변경 내역과 근거’에서 각 계획 변경 확인.
- 기존 reasoning 스트리밍, 도구 호출 과정, Raw/Workflow/Activation context 지원.

## 실행 한도와 비교

계획 최대 8단계, 갱신 최대 24회, 기록 조회 최대 4회, 조회+반응 판단 기록 기본 한도 8회, 전체 도구 호출 최대 48회. 계획 변경 뒤 최종 판단은 기록할 수 있도록 허용한다. 불완전한 계획은 한도 소진 시 강제로 완료 처리하지 않는다.

Q3 × 불신 중심/신뢰 회복에 열린 프로필, Q3a × 동일 두 프로필을 비교할 수 있다. 상담사 발화·모델·생성 설정·사전 궤적을 맞춰 비교한다. 추가 계획 호출의 비용도 별도로 집계한다.

`tests/test_q3a.py`: 모의 모델로 계획 수행, 조회·재계획, 불완전 계획/낡은 판단의 발화 확정 차단, 다음 턴 분리, 실패 롤백, 편집 독립성 검증.
`tests/browser_q3a.cjs`: 편집·저장·실행취소, 생성, 체크리스트·계획 이력, 노트, Activation/Workflow, 새로고침 복원·모바일 검증.
실제 모델의 계획 타당성과 발화 품질 개선 여부는 대화 실험에서 별도 확인한다.

## 도구 결과 전달

모델 입력에서는 `content`의 JSON 텍스트가 `structuredContent`와 같은 경우 중복 텍스트만 제외한다. 다른 설명·오류·메타데이터는 유지하며, UI와 실행 로그에는 원래 반환값 전체를 보존한다. 이전에 저장한 대화는 변경하지 않는다.

계획의 `result`는 결정한 내용과 다음 판단에 필요한 미해결 사항, `sources`는 출처를 포함한 핵심 근거를 간결하게 기록한다. 의미 판단은 모델이 하며 강제 길이 제한이나 잘라내기는 적용하지 않는다.

계획 도구는 action별 `oneOf` 스키마와 Python 검증이 같은 필드 정의를 사용한다. `start`는 action·step_id만 받으며, 완료는 별도 호출에서 result·sources와 함께 기록한다.

## 2026-10-30 공통 기록 원칙 수정

내면 판단·표현 선택·기록의 역할과 자료별 근거 범위를 구분했다. 노트와 궤적은 이미 생성된 내면·선택·발화를 선별·요약하며 대상·의미·시점·확실성을 보존한다. 기록 중 새 심리 해석이나 상호작용 결과를 추가하지 않도록 메인 지침과 도구 설명을 맞췄다. 호출 순서와 스키마는 유지한다. Q3sk는 같은 노트 지침을 기존 시점에 스킬로 제공한다.
