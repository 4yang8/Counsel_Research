# state_summary

UI의 실험 버전에서 선택한다. 여러 턴을 관찰하려면 실행 방식을 **대화 이어가기**로 선택한다.

1. 첫 생성은 편집한 초기 대화와 상태에서 시작한다. 초기 히스토리에 없는 속마음 기록은 만들지 않는다.
2. 메인이 내면상태·근거·느낌·실제 발화를 JSON으로 생성한다. 검증된 완료 응답만 상태 DB에 추가한다.
3. 다음 상담사 발화를 전송하면 같은 Gemma 모델의 별도 요약 담당이 누적된 모든 생성 턴의 내면상태·근거를 읽어 하나의 통합 흐름을 만든다. 턴별 요약을 나열하지 않는다.
4. 메인은 공개 대화, 현재 상태 수준, 통합 내면 흐름 요약으로 시작한다. 이전 내면 원문과 이전 도구 호출·결과는 기본 입력에서 제외한다.
5. 필요한 원문은 `retrieve_inner_state(query, state, reason)`로 조회한다. 상담사가 어떤 말을 했을 때 어떤 의미로 받아들여 왜 그렇게 느꼈는지를 질문으로 찾는다. 같은 Gemma 조회 담당이 가장 관련된 기록 하나를 선택하고 Python이 원문을 반환한다. 관련 기록이 없으면 null을 반환한다. 호출 기준은 `system.md`와 도구 설명에 있으며 API로 호출을 강제하지 않는다.

상태는 메인의 이번 반응 후 상태를 다음 턴의 입력으로 이어간다. 초기 상태 설정을 매턴 덮어쓰지 않는다.
요약 담당에게는 모든 내면 기록에서 상담사 발화 → 받아들인 의미 → 내면상태와 설정 근거 → 느낀 반응과 반응을 구성한 이유를 시간순으로 제공한다. 반응 전후 수준도 포함한다. 전체 공개 대화, 프로필, 내담자 공개 발화 원문은 별도로 넣지 않는다. 기록 안의 근거가 공개 발화를 설명할 수는 있다. 메인에게는 공개 히스토리를 계속 제공한다. 요약 출력은 턴별 나열 대신 전체 내면 흐름을 연결한 짧은 한 문단이다.
요약은 상태 수준의 유지·변화와 그 근거를 보존한다. 같은 수준 안의 미세한 변화도 근거가 있을 때 표현하되 기록에 없는 상승·하락은 만들지 않는다. 초기 대화에는 내면 기록이 없으므로 그 시기의 내면 흐름은 복원하지 않는다.
요약 저장·이벤트의 `source_turns`, `source_record_count`, `summary_mode`로 요약한 범위를 확인한다. 5번 생성하면 2~5번째 생성 앞에서 각각 1~4개 기록을 요약한다. 5번째 내면 기록은 다음 전송에서 요약에 포함된다.

## 저장과 확인

- 실행 로그: `sessions/state_summary/<session_id>/*.json`, `*.events.jsonl`
- 내면 DB: `sessions/state_summary/<session_id>/inner_states/*.json`
- 요약 기록: 같은 세션의 `summaries/*.json`
- UI: 현재/생성 후 상태, 요약, 내면 원문, 공개 발화를 별도로 표시한다. Raw/Workflow에서 요약 담당과 메인의 실제 입력도 확인한다.
- 실패·토큰 한도 종료·잘못된 JSON은 로그에 남고 다음 상태로 반영되지 않는다. 자동 재생성하지 않는다.

UI에서 메인 지침과 요약 지침을 편집할 수 있다. 전송값은 실행 로그에 남고 기본 프롬프트 파일은 바뀌지 않는다.
버전 전환은 새 대화를 시작한다. `basic`의 기록·도구·기본 프롬프트는 별도로 유지한다.

## 상담 턴의 입력 경계

UI는 이번 상담사 발화 하나를 전송한다. 서버는 현재 세션 DB의 정상 생성 발화로 공개 대화를 복원하고 초기 히스토리에 합쳐, 매 상담 턴 `system + user`의 새 프롬프트를 만든다. 같은 턴의 도구 실행 중에는 `assistant.tool_calls → tool → 후속 모델 호출`이 유지된다. 다음 상담 턴에는 이전 도구 메시지와 내면 JSON 전체를 그대로 누적하지 않는다. 기존 공개 메시지 배열을 보내는 호출자도 내용이 DB와 일치하면 호환된다.

도구 사용 기준·실험 지시는 지침 탭의 System prompt 또는 User prompt 과제 지침에 입력한다. 실제 상담사 발화 칸에는 상담 내용만 쓴다. 도구 정의·실행 결과는 모델 내부 참고 정보다. 실행 지시를 내담자가 상담사에게 들은 말로 취급하지 않도록 기본 메인 지침에도 구분을 명시했다.

내면 DB 원문은 기존의 `counselor_utterance`, `inner_state`, `feelings`, `utterance`를 함께 저장한다. 의미 중심 조회는 이 결합된 기록을 사용한다. 턴·ID·시점은 내부 식별과 순서 관리용으로 보존한다. 이전 `turn/state/reason` 인자 호출은 기존 로그·호출자 호환을 위해 지원하지만 새 도구 정의에는 노출하지 않는다.

Raw의 질문 전송 단계는 서버에 보낸 준비 데이터이고, 모델 호출 단계가 실제 LLM 입력이다. 완료 단계는 이번 턴의 실행 기록이며 다음 상담 턴에 그대로 전송되는 배열이 아니다.
