# 노트·조회·대화 의도 비교 실험

## 선택할 버전

실험 설정의 **내담자 버전**에서 선택하고 새 대화를 시작한다. 기존 세션은 생성 당시 버전을 유지한다.

| 조건 | 버전 | 초기 노트 | 조회 | 의도 구분 |
|---|---|---|---|---|
| A | `Q2a_trait_background` | 전체 | 없음 | 기존 반응 계획 |
| B | `Q2a_note_select` | 선택 항목 원문 | 없음 | 기존 반응 계획 |
| C | `Q2a_note_retrieve` | 선택 항목 원문 | 현재·변경·당시 기록 | 기존 계획, 재판단 가능 |
| D | `Q2a_turn_goal` | 전체 | 없음 | 대화 의도 / 표현 계획 |
| E | `Q2a_agentic_memory` | 선택 항목 원문 | 현재·변경·당시 기록 | 의도 구분, 재판단 가능 |

A~E를 처음 제작할 때는 A의 코드·프롬프트를 변경하지 않았다. 공통 UI의 선택 이름에 A 표시만 추가했다. B~E는 공통 runtime을 버전별 독립 모듈로 로드하며, 각각 별도 프롬프트 디렉터리·저장 디렉터리·잠금을 가진다. 실행 중 전역 버전을 바꾸는 방식은 사용하지 않는다.

## 실행 흐름

- B: 특성·배경·노트 ID 라우팅 → 선택 원문으로 판단 → 발화 확정 → 전체 노트 복원 → 상태 선택·항목 갱신.
- C: B의 초기 입력 → 필요시 조회 / 잠정 판단 기록·수정 → 근거 확인 종료 판단과 발화 확정 → 전체 노트로 상태 선택·항목 갱신.
- D: 기존 특성·배경 라우팅 → 전체 노트로 appraisal·대화 의도·표현 계획 기록 → 발화 확정 → 상태 선택·항목 갱신.
- E: C의 흐름에 D의 대화 의도 구분을 결합한다.

C·E는 첫 판단 기록 전에도 조회할 수 있다. 발화 확정 전에는 `stage_client_update`를 여러 번 호출해 기존 판단을 수정할 수 있다. 발화 확정 후에는 상태 선택·노트 갱신만 가능하다. 필수 기록 실패 시 발화와 노트 모두 확정하지 않는다. 같은 턴의 reasoning·도구 호출·결과는 유지한다.

## 모델의 기록 형식

공통 `appraisal`은 interpretation / immediate_feeling / relevant_evidence / uncertainty, `response_plan`은 action / reason을 유지한다.

D·E는 `stage_client_update`에 `turn_goal`을 추가한다.

- `intention`: 이번 말로 표현하거나 지키려는 바람·경계.
- `grounds`: 그 의도가 개인 정보·현재 마음에서 형성된 근거.
- `uncertainty`: 내담자가 자신의 의도에서 정하지 못한 부분.

C·E는 발화 확정 인자에 `evidence_decision`을 추가한다.

- `status`: sufficient / unavailable / budget_exhausted.
- `reason`: 조회로 확인한 내용과 판단에 미친 영향, 또는 조회 없이 결정할 근거.
- `remaining_gap`: 생성에 필요한 자료에서 아직 확인하지 못한 부분. 내담자 자신의 감정적 불확실성과 구분한다.

## 조회 도구

`retrieve_client_memory` 하나의 `source`로 대상을 나눈다.

| source | 원본 | 반환 |
|---|---|---|
| current | 현재 `state_notes.md` | 영역·항목 ID·현재 본문 |
| changes | 완료된 턴의 `note_operations` | 항목 ID·추가/수정/삭제·변경 전후·이유·턴 |
| episodes | 완료된 턴의 기록 | 상담사·내담자 발화, 당시 appraisal·계획·대화 의도 |

조회 대상은 **같은 세션의 이번 턴 시작 시점에 확정된 기록**이다. 진행 중 변경안, 미래 턴, 다른 세션, 프로필 경험 DB, 웹은 포함하지 않는다. 과거 기록의 판단은 당시 모델의 주관적 해석으로 반환한다.

검색은 별도 LLM 없이 Python이 수행한다. `query`의 공백 구분 단어를 원문 부분 문자열 OR로 검색하고 일치 단어 수, 최신 턴 순으로 정렬한다. 동의어·의미 검색은 하지 않는다. 빈 검색어는 지정 필터 내 최신 기록이다. `section`, `item_ids`, `turns`로 좁히고 `offset`, `limit`으로 이어 볼 수 있다. episodes는 turns로, current는 영역·ID로 지정한다.

### 실행 한도

- 조회 최대 4회, 조회와 잠정 판단 기록은 합쳐 최대 8회.
- 한 번에 최대 5개, 원문 합계 약 14,000자. 매우 긴 단일 원본은 앞부분 발췌임을 표시한다.
- 같은 조건 재요청은 재검색 없이 `no_new_evidence`를 반환하며 조회 횟수에 포함한다.
- C·E 전체 도구 호출 최대 20회(잘못된 인자에 대한 재시도 포함). B·D는 기존 설정의 호출 한도를 사용한다.
- 한도가 차면 조회 도구를 제외하고 판단·발화 확정·노트 갱신을 마칠 수 있게 한다. 근거가 충분하다는 모델의 보고와 실제 한도 도달 여부는 별도 기록한다.

원본 조회 결과가 빈 것은 자료를 찾지 못했다는 뜻이며, 내담자의 기억 상태를 판정하는 로직은 없다. 변경 이력 조회는 항목별 변경 기록이 있는 새 실험 턴을 대상으로 한다.

## UI·파일

- 버전별 폴더의 `system.md`, `user.md`, `trait_router.md`, `trait_router_user.md`를 기존 프롬프트 UI에서 조회·수정·저장할 수 있다.
- 채팅의 reasoning·도구·diff, Raw context, Workflow, 노트 탭은 기존 방식으로 연동한다.
- 버전 기록에 노트 선택 ID, 대화 의도, 조회 요청·결과, 종료 판단을 추가 표시한다.
- Activation context는 user prompt를 세부 구역·노트 항목으로 나누며, 입력하지 않은 현재 노트 항목은 회색이다. 이 회색 원문은 표시용 이벤트에만 있고 모델 payload에는 없다. 발화 확정 후에는 전체 노트가 활성화된다.
- appraisals 기록에 선택 ID, 판단 수정 이력, 조회 이유·결과·출처, 종료 판단, 실제 요청, 라우터 입출력, 에이전트별 토큰 사용량을 저장한다. 기존 실행 로그에는 스트리밍 reasoning과 호출 순서가 남는다.
- 메인 system prompt 등 세션 설정은 기존처럼 새 대화 생성 시 고정된다. user 템플릿과 라우터 지침은 각 호출 때 파일을 읽는다.

## 검증 범위

모의 모델과 실제 HTTP·브라우저 경로로 컨텍스트 경계, 조회·재판단, 저장, 오류 처리, 프롬프트 분리, UI를 검증한다. 실제 모델의 상담 발화 품질이나 A~E 간 효과 차이는 별도의 생성 실험으로 확인해야 한다.

검증 결과: 새 실험 통합 테스트 8개, 기존 기능 회귀 테스트 25개 통과. 브라우저에서 B~E 생성·노트·Workflow·프롬프트 조회·세션 복원을 확인했고, E의 다음 턴에서 미선택 노트 회색 표시와 발화 후 전체 노트 활성화를 확인했다. 기준선 파일 해시는 `baseline_source_hashes.json`에 남겼다.

## 2026-10-23 · 라우터 범위 정리와 F 추가

- A~E의 `trait_router.md`와 공통 출력 스키마의 `relevance` 설명을 수정했다. 현재 대화 단서와 선택 자료의 관련성을 1~2문장으로 작성하도록 범위를 명확히 했다. 입력 자료의 의미, ID 선택, 관련 노트 원문 선택 방식은 유지한다.
- 이전의 기준선 해시는 초기 A~E 제작 당시 기록이며, 이번에 수정한 라우터의 해시를 뜻하지 않는다. 이미 저장된 세션의 요청·출력 기록은 변경하지 않았다.
- F(`Q2a_agentic_memory_F`)는 위 수정을 반영한 E를 복제한 개발 버전이다. 초기 기능과 프롬프트는 E와 동일하며, 실험 실행 코드·도구·노트·컨텍스트 구성 파일을 F 폴더에 따로 두었다. 공통 UI·연결·저장 기반은 공유한다. 세부 위치는 `../Q2a_agentic_memory_F/README.md`를 참고한다.

### F 후속 변경 · 자유 글머리 노트

F는 고정된 10가지 상태와 현재 내면의 세 영역을 제거했다. 초기 노트는 제목과 `(내용 없음)`이며, 발화 확정 뒤 `update_client_notes`로 항목별 변경을 적용한다. A~E는 기존 구조를 유지한다.
