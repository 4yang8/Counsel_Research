# 그룹1 선택 조회 실험: 15개 × 2세트

30개 모두 완료했다. **자유 선택 조건은 15개 모두 도구를 쓰지 않았고, 최소 호출 지시 조건은 15개 모두 한 번씩 호출했다.** 같은 Gemma 서브에이전트가 정보 한 개를 선택하는 구조는 정상 작동했지만, 초기 정보가 부족한지 판단하여 자발적으로 조회하는 행동은 이번 배치에서 관찰되지 않았다.

조회가 도움이 된 부분은 개인 경험의 근거와 구체성이다. 반면 상담사의 말에 대한 감정 방향과 대화의 자연스러움은 대체로 유사했다. '도구 호출이 있었다'를 곧바로 '발화 품질이 좋아졌다'로 해석하면 안 된다.

## 실험 범위와 통제

- 배치: `group1_selective_30_20261008T100555Z`의 신규 30개만 집계했다. 이전 배치 `group1_full_context_15_20261008T063458Z`의 15개는 재생성하지 않고 참고했다.
- 프로필: 한글 원본 001·002·005·007·008, 각각 히스토리 3개. 원본 자료와 히스토리는 가상 사례다.
- 이전 15개와 같은 상담사 발화, 대화 히스토리, 상태 수준과 의미, task, taxonomy, 생성 설정을 사용했다. 각 히스토리 마지막 내담자 원문은 보내지 않았다.
- 각 입력을 자유 선택 → 최소 호출 순서로 번갈아 실행했다. 두 신규 조건의 최초 payload는 시스템 문구 외에 동일함을 15쌍 모두 검증했다.
- Gemma: `google/gemma-4-31B-it`, temperature 0.7, top_p 0.95, 메인 최대 출력 1024, seed 미지정. 별도 모델 평가기를 쓰지 않고 원문과 로그를 검토했다.

시스템 지침은 다음 두 가지다. API의 `tool_choice`로 필수 호출을 강제하지 않았다.

```text
자유 선택:
주어진 툴을 적절히 활용하세요.

최소 호출:
주어진 툴을 적절히 활용하세요.
최종 내담자 발화를 생성하기 전에 제공된 도구를 적어도 한 번 호출하세요.
```

두 신규 세트에는 아래 조회 도구 두 개만 제공했다. 기존 일반 위임과 대학원생 자료 도구 5개는 이 실험에서는 제공하지 않았다. 그 외 메인 지침을 더 강하게 고치지 않았다.

## 구현한 정보 경계

| 구분 | 정보 |
|---|---|
| 처음부터 제공 | 나이·직업·생활 단계·배경, 현재 고민, 핵심/중간 신념, 대처 경향, 현재 상태와 의미, 대화, taxonomy |
| 성장 경험 DB | 원본 프로필의 `childhood_data`; `retrieve_childhood(reason, query)` |
| 상황 기록 DB | 원본 프로필의 `situations`; `retrieve_situation(reason, query)` |

기본 배경과 히스토리에 이미 언급된 사실은 삭제하지 않았다. 예를 들어 아버지의 죽음이 기본 배경에 있으면 메인이 처음부터 안다. 따라서 모든 DB 사실이 최초 입력에 완전히 숨겨진 실험은 아니다. 프로필을 물리적으로 여러 파일로 나누지 않고, 동일한 원본 JSON의 필드별 DB 뷰로 나눴다. 현재 기본 `profile_context_mode`는 `selective`이며 `full`로 설정하면 전체 입력 방식으로 돌아간다.

각 호출은 다음 흐름이다.

1. 메인이 부족한 정보와 조회 질문을 `reason`, `query`로 작성한다.
2. Python이 해당 프로필의 해당 DB만 읽어 별도 Gemma 컨텍스트를 만든다. 자식 시스템 지침은 개발자가 정의한 조회 역할이다.
3. 자식은 레코드 ID 하나 또는 null을 출력한다. 같은 Gemma 모델을 쓰며 도구는 없고 최대 출력은 128토큰이다.
4. Python이 ID를 검증하고 해당 원문 하나만 부모의 `role: tool` 메시지에 넣는다. 자식의 전체 DB·대화는 합치지 않는다.
5. 메인이 시스템 지침·기존 입력·호출 인자·도구 결과를 포함한 누적 컨텍스트로 다시 응답한다.

성장 경험은 원문 문장 하나, 상황 기록은 사건 하나와 당시 생각·감정·신체 반응·행동을 한 단위로 반환한다. 후자는 여러 필드지만 하나의 사건 기록이다. 자식에게 새로운 요약 사실을 생성시키는 대신 원문을 반환하여 근거 일치 여부를 확인하기 쉽게 했다. 조회 담당이 현재 감정을 결정하거나 상태를 갱신하지 않는다.

## 호출과 비용

| 조건 | 완료 | 호출한 사례 | 도구 호출 | 원문 반환 / 일치 없음 | 총 LLM 호출 | 총 토큰 | 평균 소요 시간 |
|---|---:|---:|---:|---:|---:|---:|---:|

| 이전 전체 입력 | 15/15 | 0/15 | 0 | 0 / 0 | 15 | 61,673 | 14.14초 |
| 축소 입력·자유 선택 | 15/15 | 0/15 | 0 | 0 / 0 | 15 | 40,118 | 12.61초 |

최소 호출 조건의 LLM 호출 45회는 **메인 30회 + 조회 담당 15회**다. 15개의 조회 중 성장 경험 5개, 상황 기록 10개를 호출했다. 도구 실행 오류, 존재하지 않는 ID 반환, 다른 프로필 자료 혼입은 0건이었다. 자식 15개 모두 정상 종료했으며, 원문이 반환된 13개는 DB의 정확한 한 레코드였다. 나머지 2개는 정상적인 `no_match`다.

입력/출력 토큰은 자유 조건 36,530 / 3,588, 최소 호출 조건 91,594 / 5,567이다. 최소 호출 조건에서 조회 담당만 사용한 토큰은 12,494이다. 평균 시간은 모델만의 생성 시간이 아닌 앱의 스트리밍·로그 저장을 포함한 요청 소요 시간이다.

동일한 두 도구 정의를 놓고 전체/축소 입력을 추가 **토큰화만** 해 비교했다. 최초 입력 평균은 3,295.3 → 2,435.3토큰, **860토큰(26.1%) 감소**했다. 추가 대화는 생성하지 않았다. 이전 전체 입력과 자유 조건의 차이에는 기존 5개에서 조회 2개로 줄인 도구 스키마 차이도 섞여 있으므로, 전부 DB 축소 효과로 계산하지 않았다.

최소 호출 조건의 총 토큰은 이전 전체 입력보다 약 57.5%, 새 자유 조건보다 약 142.2% 많았다. 메인 재호출은 기존 컨텍스트를 다시 입력하므로, 초기 입력을 줄여도 한 번의 조회에서 비용이 더 커질 수 있다. 이것은 이번 작은 DB와 짧은 단일 응답의 결과이며 대규모 DB·여러 턴으로 일반화할 수 없다.

### 근거를 실제로 보강한 사례

**001_h2**는 과거 경험을 직접 묻는 질문이다. 자유 조건은 조회 없이 “솔직한 마음을 말했다가 이기적인 아이라는 소리를 들었다”고 답했다. 최초 정보에는 없는 부모 발언이며, 001의 성장 자료는 부족한 모습 감추기와 형제 비교 중심이다. 최소 호출 조건은 원문의 “힘들어하거나 실수하는 모습을 보이면 남들 앞에서 감추도록 요구받음”을 읽고 그 배경을 발화에 연결했다. 스키마에 어울리는 일반적인 기억을 생성하는 대신 해당 인물의 자료를 사용한 차이가 있다.

**002_h2**는 두 조건 모두 미안함의 배경을 설명했지만, 조회 조건은 “네가 누나니까 양보해야지”, “엄마 힘든 거 안 보이니”와 이기적이라는 핀잔을 근거로 더 개인적인 설명을 만들었다. **008_h3**도 조회된 자동 생각과 가슴 뻐근함을 가져와 딸의 울음에 대한 당혹감과 해결책을 서두르는 이유를 구체화했다. 이 두 사례는 감정 라벨이 바뀌어서가 아니라 개인 맥락이 구체적으로 반영됐다는 점에서 유망하다.

### 조회했지만 공개하지 않아도 되는 사례

**005_h2**는 조회 결과의 불안·공허함을 그대로 모두 말하지 않고, 낮은 자기개방에 맞춰 “집이 넓게 느껴진다”, “좀 허전하다” 정도로 표현했다. **007_h3**는 어린 시절의 신념을 조회했지만 현재 이야기부터 하겠다고 선택했다. 정보가 내면 판단의 참고가 되는 것과 그 정보를 실제 발화로 공개하는 것은 구별되어 작동했다.

**001_h1**, **002_h3**, **005_h3**은 조회를 해도 실제 발화가 크게 달라지지 않았다. 특히 002_h3에서 가져온 신념 문장은 초기 핵심 신념과 의미가 겹친다. 최소 호출 지시가 유효한 조회 필요성까지 보장하지는 않는다.

### 상태 반영은 별도 문제로 남음

**001_h3**은 두 신규 조건 모두 높은 변화 자신감을 반영해 친구에게 물어보겠다고 했다. 이전 전체 입력에서는 높은 자신감에도 더 생각할 시간이 필요하다고 답했다. 이번 자유 조건도 잘 반영했으므로 이 개선을 조회 때문이라고 볼 수 없다.

**002_h1**은 높은 변화 자신감에도 자유 조건에서 “실제로는 어려울 것 같아요”, “바로 해준다고 하는 게 편할 것”이라며 제안을 피했다. 조회 조건은 몸 상태 확인을 해볼 수 있다고 답해 상대적으로 상태와 잘 맞았다. 하지만 한 번의 확률적 생성이고 다른 해석도 가능하므로, 도구가 상태-히스토리 충돌을 해결했다고 결론 내리지 않았다.

### 일치 없음과 해석의 주의점

**005_h1**의 질문은 폭언 바로 당시의 구체적인 사건·생각·감정이었다. DB에는 HR의 상담 권유 이후 상황이 있으며 바로 그 폭언 장면의 세부 기록은 없어 null을 선택했다. **007_h2**의 질문은 실제 짧은 외출 시도 기록이었다. DB의 제주 워크숍 거절과 운동 제안 회피는 해당 기록과 같지 않아 null을 선택했다. 빈 결과를 도구 오류나 기억 부재로 처리하지 않았다.

조회 조건에서도 007_h2는 “집 앞 편의점 가는 것도 망설여진다”는 구체화를 생성했다. 원문에는 없는 표현이다. 현재 두려움을 표현하는 허용 가능한 창작으로 볼지 별도의 과거 사실로 볼지는 연구의 생성 기준에 달려 있다. 단순한 세부 확장을 모두 오류로 처리하지 않았다.

008_h2의 자유 조건은 “지금 하신 그 말을”이라는 질문을 “지금 바로 하라”는 요구로 강화했다. 조회 조건은 그 직접 인용은 줄었지만 아내가 방으로 간 행동을 “부정적인 피드백”으로 해석했다. 관찰된 행동과 내담자의 주관적인 해석을 구분할 필요는 계속 있다.

## 감정 라벨과 자연스러움

라벨은 각 출력에서 모델이 직접 명시한 항목을 집계했다. 복수 선택이 있어 합계는 15보다 클 수 있다.

| 라벨 | 이전 전체 입력 | 자유 선택 | 최소 호출 |
|---|---:|---:|---:|
| 이해받음 | 8/15 | 10/15 | 11/15 |
| 선택권 존중 | 6/15 | 7/15 | 3/15 |
| 부담·압박 | 7/15 | 5/15 | 3/15 |
| 오해받음 | 1/15 | 1/15 | 1/15 |

감정 라벨의 차이를 품질 점수로 해석하지 않았다. 최소 호출에서 선택권 라벨은 줄었지만 판단 이유에는 속도·경계 존중이 종종 언급돼, 정보 조회 효과 외에 출력 라벨 선택의 변동도 섞여 있다. 005의 실적 중심 방어, 007의 신체 위험 우려, 008의 감정 표현 어려움은 두 조건 모두 유지되었다. 신규 30개에서 나이·직업·가족 구성이나 사건 결과를 명백히 뒤집는 모순은 검토상 발견하지 못했다.

대화는 대부분 앞선 고민과 질문에 이어지는 답을 만들었다. 하지만 “잠시 침묵/한숨 → 좀 마음이 놓이네요” 같은 형식은 반복된다. 괄호로 동작을 쓰는 발화는 자유 조건 12/15, 최소 호출 10/15로, 조회만으로 문체의 반복이 해소되지는 않았다. 긴 DB를 읽었다는 이유로 발화가 일괄 길어지거나 자기개방이 자동으로 높아지는 현상은 나타나지 않았다.

## 이번 결과의 의미

1. **조회 실행 능력과 조회 필요성 판단은 다르다.** 강제 지시 조건에서는 15/15 정상 호출했으므로 두 도구를 사용할 수 있다. 그러나 과거 경험을 물었던 자유 조건의 001_h2와 002_h2까지 조회하지 않아, 이 설정에서 필요한 개인 사실을 조회하는 선택은 충분히 관찰되지 않았다. 모델이 도구를 이해하지 못했다고 단정할 근거는 아니다.
2. **가장 뚜렷한 효과는 개인 사실의 근거와 반응 묘사의 구체성이다.** 전체 입력을 빼도 현재 감정 방향과 기본 성격은 유지되는 사례가 많았다. 반응의 적절성·상태 반영·자연스러움까지 일괄 개선한 것은 아니다.
3. **작은 현재 DB에서는 매번 조회하면 비용이 커진다.** 초기 컨텍스트를 줄이는 것은 확인됐지만 강제 조회를 기본 운영 정책으로 권할 근거는 아직 부족하다.
4. **조회 질문 자체도 관찰해야 한다.** 001_h3와 008_h2는 부정적 경험/실패를 찾는 방향으로 질문을 만들었다. 기존 가설을 확인하는 조회인지 새로운 정보를 확인해 판단을 바꾸는 조회인지 구분할 필요가 있다. 이번 결과만으로 실제 내부 원인이나 사고 과정을 확정할 수 없다.

각 입력을 1회만 생성했고 seed를 고정하지 않았다. 자유/최소 호출은 입력을 맞췄지만 확률적 변동이 남는다. 이전 전체 입력 대비는 정보량과 도구 스키마도 달라졌다. 상태 조합도 히스토리마다 다르므로 특정 상태의 독립 효과를 추정하지 않았다. 이 보고서의 판단은 한 번의 배치와 원문 검토 범위에 한정된다.

## 파일과 확인 방법

- [manifest.json](manifest.json): 조건, 모델, 생성 설정, 원본 해시, 제한점.
- [analysis.json](analysis.json): 완료/호출/토큰 통계, 15쌍 입력 동일성 검증, 원문 반환 검증, 정성 검토.
- [outputs.md](outputs.md): 30개 발화와 조회 질문·반환 원문.
- [results.json](results.json): 사례별 결과와 부모/자식 로그 경로.
- `optional/case_*`, `required/case_*`: 정확한 input, payload, events, result.
- `sessions/`: 원본 부모·자식 이벤트와 요청 로그. `snapshot/`: 실행 시 코드와 DB 원본.
- [token_control.json](token_control.json): 동일한 두 도구 조건의 토큰화 비교.

기존 UI 앱은 재시작한 뒤 그룹1 프로필/히스토리를 선택하면 축소된 프로필이 적용된다. **자료·도구에서 `retrieve_childhood`, `retrieve_situation`만 켜면** 이번 실험의 도구 조건을 사용할 수 있다. 최소 호출 조건은 위 시스템 문구를 넣는다. 기존 vLLM 서버 설정이나 재시작은 필요하지 않다. 다른 도구 선택은 자유롭게 유지할 수 있으며 자동으로 기존 도구를 삭제하지 않았다.

검증: 상담 실습 Python 테스트 16개 통과, 실제 브라우저 검사 통과, 생성 30개 모두 `completed`/`stop`, 자식 선택 15개 모두 `stop`, 15쌍의 입력 통제와 한 레코드 반환 검증 완료.
