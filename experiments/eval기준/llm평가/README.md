# LLM 평가 프롬프트 · 초안 v2

## 기준 개정 v2

- ①은 과거 이유의 내용, ②는 과거·현재의 시간 관계, ③은 현재 개입에 대한 심리적 반응, ④는 현재 공개 경계와 표현의 부합을 평가한다. 동일한 '정확한 답변'을 네 항목에 자동으로 중복 가점하지 않는다.
- 각 항목에 적용 여부 → 근거 충분성 → 1~5점 순서를 명시했다. 4점은 관찰되는 작은 불일치, 3점은 실제 부분 오류이며 단순한 의심·근거 부족의 기본값이 아니다.
- ③은 현재 반응이 없고 과거 이유만 설명하면 해당 없음으로 처리한다. 현재 반응은 있으나 판단할 상태·개입 근거가 부족하면 판정 불가다. 자료로 확인되는 간접 효과는 허용하고, 개입이 직접 언급하지 않았다는 이유만으로 오류를 확정하지 않는다.
- 현재 첫 사례의 응답 예시 1은 ③의 단순 과거 이유 설명 제외 조건에 해당한다. 이 설명은 사용 안내이며 평가 입력에 포함하지 않는다.
- 평가 출력 스키마는 유지한다. 기존 results는 당시 기준의 결과로 보존하고, 다음 실행부터 개정 프롬프트를 읽는다. 이후 저장 방식은 아래 설명처럼 대화별 MD 하나로 간소화했다. 개정 기준의 실제 모델 재평가는 아직 하지 않았다.

한 호출은 **한 답변 × 한 평가 항목**이다. 같은 답변에 네 항목을 각각 적용할 수 있지만 적용 불가·근거 부족을 허용한다. 처음에는 항목별 결과를 따로 보고 종합점수는 만들지 않는다.

- system 파일 전체를 system message로 전달한다.
- JSON 파일은 코드에서 읽고 검증한다. `format_evaluation_input`이 프로필·턴별 발화·내면 기록·직전 상태를 텍스트로 변환해 user 파일의 `{{evaluation_input_text}}`에 넣는다. 모델에는 입력 JSON 구조나 사례·답변 ID를 전달하지 않는다.
- 모델 조건(public/selection/full), 제작자 메모, 좋은/나쁜 답변이라는 이름, 기대 점수, 다른 후보 답변은 숨긴다.
- 평가자는 과거 이유와 비교할 수 있도록 **확보된 평가용 과거 내면 기록 전체**를 본다. 발화 생성기가 실제로 제공받은 기억만 주면 기억 누락에 따른 왜곡을 판정할 기준도 함께 사라진다.
- 실제 주입 기록·선별 결과는 별도 로그 분석용으로 보존하되 기본 LLM 품질 평가 입력에서는 제외한다. 조건마다 동일한 기준 자료를 사용한다.
- 현재 응답의 내면 기록은 파일의 `target.generated_inner`에서 읽어 「이번 발화의 내면 기록」으로 제공한다. 이것은 생성 결과이지 독립적인 심리 정답이 아니다. 조건 간 입력 유무도 가능한 한 통일한다.
- 완료된 응답 이후의 기록은 넣지 않는다. 응답 결과로 갱신된 상태를 그 응답 이전의 정답처럼 넣지 않는다.

## 실행기에 넣는 JSON 파일 형식

```json
{
  "case_id": "case_01",
  "response_id": "response_1",
  "profile": {"name": "민수", "presenting_problem": "수면 문제"},
  "history": [
    {
      "turn": 1,
      "counselor_utterance": "상담사 발화",
      "client_utterance": "내담자의 실제 공개 발화",
      "private_inner": {
        "appraisal": {"interpretation": "당시 해석", "immediate_feeling": "당시 감정", "relevant_evidence": "근거", "uncertainty": "불확실성"},
        "turn_goal": {"intention": "당시 의도", "grounds": "근거", "uncertainty": "불확실성"},
        "response_plan": {"action": "말하거나 보류할 내용", "reason": "이유"}
      }
    }
  ],
  "reference_state_before_target": null,
  "target": {
    "turn": 2,
    "counselor_utterance": "평가 지점의 상담사 질문 또는 개입",
    "client_utterance": "평가할 답변 한 개",
    "generated_inner": null
  }
}
```

`reference_state_before_target`을 사용할 경우 `content`와 `source`를 가진 객체로 넣는다. 예: `{"content": "직전 시점에 별도로 확인된 상태", "source": "해당 상태 기록의 식별자"}`. 현재 사례에서는 별도 자료가 없으므로 null로 두며, history의 마지막 내면은 그대로 참고할 수 있다. 자료가 없을 때 빈 내용을 만들어 채우지 않는다.

## 모델이 읽는 입력

```text
[내담자 프로필]
이름: 민수
상담 주제: 수면 문제

[과거 대화와 당시 내면 기록]
[1턴]
상담사 발화: …
내담자 발화: …
당시 내면 기록:
상황 해석:
  해석: …
이번 발화의 목표:
  의도: …

[별도로 확보한 평가 대상 직전 상태]
제공되지 않음

[평가 대상: 2턴]
상담사 발화: …
평가할 내담자 발화: …
이번 발화의 내면 기록（생성 결과·보조 자료）:
제공되지 않음
```

내용은 LLM으로 요약하거나 재작성하지 않고 원문을 유지한다. 코드가 구조 이름만 한국어 항목명으로 바꾸며 누락·빈 자료는 「제공되지 않음」으로 표시한다. 새로운 영문 구조 항목을 추가할 경우 `RECORD_LABELS`에 한국어 이름을 추가하거나 입력의 항목명을 한국어로 작성한다. 알 수 없는 구조를 조용히 생략하지 않는다. 원문 내용이나 출처 자체에 포함된 영문 표현은 그대로 보존한다. 출력은 기존처럼 판정 상태·점수·이유의 JSON이며, 결과 MD의 작은따옴표와 큰따옴표는 그대로 표시한다.

## 기존 사례 연결

[입력예시_01_response_1.json](입력예시_01_response_1.json)은 상위 폴더의 첫 사례에서 응답 예시 1만 선택해 변환한 실제 입력 예시다.

- `private_records` → `history` (`utterance` → `client_utterance`, `inner` → `private_inner`). 공개 대화와 턴의 대응을 확인한 뒤 합친다.
- `evaluation_point.counselor_utterance` → `target.counselor_utterance`.
- 평가할 `response_examples` 항목 하나 → `response_id`, `target.client_utterance`.
- `author_notes`, 다른 응답 예시, `generation_input.condition`은 제외한다.
- 원본 예시 데이터는 수정하지 않았다. 응답 예시 2·3을 평가할 때는 응답 식별자와 대상 발화만 교체한다.

첫 사례는 과거 이유 충실성 평가가 중심이다. 명백한 시간 변화·개입 반응·공개 준비도 근거가 없는 항목에는 억지로 점수를 주지 않는다. 특히 현재 공개 준비도가 불명확하면 이유를 솔직히 설명했다는 사실만으로 공개 적절성 5점을 줄 수 없다.

## 결과 취급

- `scored`이면 score는 1~5 정수, 나머지 상태에서는 null이다. 0점이나 자동 3점으로 대체하지 않는다.
- 각 항목의 점수와 함께 scored/판정 불가/해당 없음의 수를 별도로 집계한다. 판정 불가를 제외한 평균만으로 조건의 우열을 결정하지 않는다.
- 이 점수는 검증 전의 순서형 기준이다. 1→2와 4→5의 차이가 동일한 크기라고 가정하거나 임상적 성공 점수로 사용하지 않는다.
- 이유를 숨기는 응답은 기억 오류인지 의도적인 표현인지 구별할 자료가 부족할 수 있다. 점수만으로 오류 원인까지 결론내리지 않는다.
- 위 프롬프트는 평가 기준 초안이며 아직 LLM 벤치를 실행하거나 사람 판정과의 일치도를 검증하지 않았다. 예시별 판정과 근거를 검토하며 경계를 조정한다.

## 평가 실행

`run_eval.sh` 상단의 설정을 편집하고 다음 명령만 실행한다. 별도 명령행 옵션은 받지 않는다.

```bash
cd /home2/sjyang114/Counsel_Research_dynamic_client_new/experiments/eval기준/llm평가
./run_eval.sh
```

- 기본: `EVAL_MODE="codex"`, `CODEX_MODEL="gpt-6-luna"`, `CODEX_EFFORT="max"`.
- 현재 셸의 입력은 세 번째 사례의 응답 예시 1이고, `CRITERIA="all"`이므로 네 항목을 순서대로 독립 호출한다. `"01"` 또는 `"01,04"`처럼 일부 항목만 지정할 수 있다.
- `INPUT_FILE`은 평가기용 JSON 경로다. 원본 사례 JSON 전체는 거절한다. 다른 답변은 별도 입력 JSON으로 저장해 지정한다.
- `EVAL_MODE="vllm"`으로 바꿀 때는 `VLLM_URL`, `VLLM_MODEL`을 실제 서버에 맞춘다. `/chat/completions`와 vLLM `structured_outputs.json`을 사용하며 지원하지 않는 서버는 오류로 표시한다. 인증이 필요하면 키 자체가 아닌 `VLLM_API_KEY_ENV` 환경변수 이름을 설정한다.
- `DRY_RUN="true"`는 실제 모델을 호출하지 않고 입력·프롬프트 구성을 확인한다. 결과 MD에는 각 항목을 「호출 안 함」으로 표시한다.
- Python 표준 라이브러리만 사용한다. Python 경로는 `PYTHON_BIN`에서 변경한다.

### Codex 실행과 인증

기존 ChatGPT 로그인을 재사용한다. 실행 전 `codex login status`가 ChatGPT 인증인지 확인하며, 미인증이면 `codex login` 또는 `codex login --device-auth`로 로그인한다. API 키 인증으로 자동 전환하지 않으며 Codex 하위 프로세스에서 `OPENAI_API_KEY`·`CODEX_API_KEY`·`OPENAI_BASE_URL` 재정의를 제외한다. 인증 파일·계정 토큰은 평가 결과에 저장하지 않는다.

평가별 빈 임시 작업 디렉터리, 새 ephemeral 세션, read-only sandbox로 실행한다. 사용자 config와 프로젝트 문서의 평가 개입을 줄이고 셸·웹 검색·하위 에이전트·이미지 도구를 비활성화한다. 관측된 실행 이벤트에 외부 도구 사용이 있으면 해당 결과는 실패로 분리한다. 관리형 지침이나 Codex 자체 기본 지침까지 API와 동일해지는 것은 아니다.

vLLM은 system/user 메시지로 전달하고, Codex는 system 파일을 `developer_instructions`, 치환한 user 파일을 stdin으로 전달한다. 내용 기준은 공유하지만 역할 계층과 실행 환경은 동일하지 않다. 모델·effort를 다른 값으로 대체하지 않으며 계정에서 지원하지 않으면 오류로 남긴다.

### 결과

실행별 폴더에 **대화 하나당 MD 하나만** 저장한다. 현재 실행기는 `INPUT_FILE`로 지정한 대화의 대상 답변 한 개를 평가한다.

```text
results/
└── 날짜_시각_모드_고유번호/
    └── case_01_past_reason.md
```

파일에는 평가 모델·effort, 평가 턴·답변 ID, 항목별 점수/판정 상태와 이유만 남긴다. 평가 진행 중에는 같은 파일을 갱신하며 미완료 항목은 「대기/평가 중」으로 표시한다. 판정 불가·해당 없음·실행 실패를 점수와 구분한다.

`summary.json`, `summary.md`, `input.json`, `config.json`, 항목별 하위 폴더, 프롬프트 복사본, 원본 응답·이벤트 로그는 results에 저장하지 않는다. Codex 실행 등에 필요한 임시 파일은 임시 디렉터리에서 처리하고 정상 완료·실패·사용자 중단 후 정리한다. 이전 실행의 기존 결과 파일은 변경하거나 삭제하지 않는다.

모델은 `status`(판정 상태), `score`(1~5점 또는 null), `rationale`(근거를 포함한 자연어 이유)만 반환한다. 관련 턴·기록 종류와 불확실성도 이유 안에 설명하며, 별도 근거·한계 필드나 근거 개수 제한은 없다. 사례·답변·평가 항목 ID는 코드가 입력과 실행 설정에서 붙인다. JSON 경로·원문 문자열 일치 검사는 하지 않는다. 출력 형식·점수 범위·판정 상태와 점수의 일치·비어 있지 않은 이유만 검증하며, 근거 내용의 정확성은 코드로 판정하지 않는다. 항목별 상세 평가 기준과 해당 없음·판정 불가 구분은 유지한다.

호출 실패·잘린 출력·형식 오류는 점수나 판정 불가로 바꾸지 않고 같은 MD에 「실행 실패」와 간단한 오류 이유를 기록한다. 다른 항목은 계속 실행하며 하나라도 실패하면 종료 코드는 1이다. 자동 재호출·다른 모델로의 대체는 하지 않는다. 다시 실행하면 기존 결과를 덮어쓰지 않고 새 폴더에 저장한다.

### 동작 점검

```bash
python3 test_run_eval.py
```

입력 누출·미래 턴·점수/판정 불일치·빈 판단 이유를 거절하고, 세 필드 출력과 코드의 식별자 부여가 맞는지, Codex가 지정 모델·effort·지침으로 호출되는지, 도구 사용 판정을 제외하는지, vLLM HTTP 형식과 잘린 응답 처리가 맞는지 모의 호출로 검사한다. 성공·실패·재실행·드라이런에서 대화별 MD만 남는지, 임시 파일이 정리되는지, 기존 결과가 보존되는지도 검사한다.
