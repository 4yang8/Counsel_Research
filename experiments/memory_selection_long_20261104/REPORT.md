# 30턴: 짧은 기록과 긴 기록의 RAG·LLM 선별 비교

## 범위

동일한 30개 과거 사건과 공개 대화를 사용하고 비공개 기록의 표현을 바꿨다. 질문10개 × 반복2 × 방법2 × 길이2 = 80개 선별 호출이다. 모든 조건에서 공개 대화와 현재 질문은 동일하며, 정답 기준은 실행 전에 고정하고 모델 입력에서 제외했다. 실제 대화나 비공개 기록을 모델로 생성하지 않았다.

짧은 비공개 기록은 평균137자, 긴 기록은 평균1114자(JSON 키 포함)다. 긴 기록은 해석·감정·검토 과정·불확실성·의도·표현 계획을 포함하며 원래 핵심 이유와 보류 내용을 그대로 보존했다. 순수 길이만 바뀐 것이 아니라 부연 내용과 스키마도 달라졌다.

RAG 시간은 검색어 생성과 임베딩/검색을 포함한다. 입력·출력 토큰은 생성 모델 사용량이고 임베딩 GPU 비용과 후속 내담자 발화는 제외한다. short를 먼저 실행한 순차 실험이라 캐시·서버 부하 영향을 통제하지 못했다. 긴 문맥을 읽는 실제 시간이 항상 토큰 수에 비례한다고 가정하지 않는다.

## 범위와 한계

- 30턴의 통제 비교이므로 이전 60턴 실험과 점수를 바로 이어붙이지 않는다. 후보 감소와 공개 대화 축약이 함께 일어났다.
- long은 짧은 기록에 반복 문장만 붙인 조건이 아니다. 핵심 의미는 보존했지만 상세한 해석과 표현 계획이 추가되고 스키마도 변했다.
- 정답은 같은 분석자가 작성한 인공 사례 기준으로 독립 검증되지 않았다. 두 반복은 두 독립 내담자 사례가 아니다.
- 전체 기록이 32768 문맥 한도에 들어가는 상황만 평가했다. 입력은 자동 절삭하지 않았다.
- RAG는 유사도 하한 없이3개를 채우고 LLM은0~3개를 선택할 수 있다. 빈 결과와 관련성 차이는 반환 정책도 반영한다.
- 현재 질문의 비교 대상이 검색어 작성 중 누락될 수 있다. 검색어 생성 단계와 임베딩 검색 단계를 구별해야 한다.
- 선택 성능은 최종 상담 발화의 정확성·정보 보호·개입 반응 타당성의 증거가 아니다.

## 동일 검색어 보조 진단 및 판단

본 실행에서는 같은 공개 입력·seed로 별도 호출해도 일부 검색어가 달라졌다. 따라서 두 길이 조건의 RAG 차이를 그대로 길이 효과라고 볼 수 없다. 짧은 조건에서 생성한 20개 검색어 전부를 수정 없이 두 후보군에 적용했다.

| 같은 검색어로 검색 | 짧은 기록 | 긴 기록 |
|---|---:|---:|
| 필수 원본 모두 확보 | 14/16 | 15/16 |
| 평균 핵심 재현율 | 93.75% | 96.875% |
| 평균 관련 기록 비율 | 79.17% | 83.33% |

이 보조 진단에서는 긴 기록이 더 나쁘지 않았다. 본 비교의 긴 RAG 13/16은 검색어가 따로 생성된 조건이며 위 진단과 합산하지 않는다. 상세는 [진단 계획](MATCHED_QUERY_PROTOCOL.md)과 [원본 결과](matched_query_results.json)에 있다.

LLM 선별은 긴 기록에서도 필수 원본16/16을 확보했다. 입력은 평균4301.5→16659.5토큰으로 약3.87배 늘었지만 평균 시간은4.52→4.25초였다. 서버의 문맥 캐시 가능성, 조건 실행 순서, 출력 토큰 감소(평균486.55→453.3) 등 영향이 함께 있고 캐시 사용량을 직접 계측하지 않았으므로 긴 입력이 무료이거나 더 빠르다고 일반화할 수 없다. 전송 입력 토큰이 늘었다는 점과 측정 지연이 비례해 늘지 않았다는 사실을 구별해야 한다.

이번 한 인공 사례의 관측 범위에서는 LLM 전체 읽기가 정확성 측면에서 안정적이었다. RAG의 실패 원인을 긴 청크나 임베딩 모델만으로 설명할 수는 없으며, 질문의 여러 비교 대상을 검색어에 보존하는 문제가 남는다. 전체 기록이 문맥 한도 안에 있는 30턴에서의 결과이며 더 긴 상담·다른 내담자로 일반화하지 않는다.
