# state_summary · 한 세션 10회 도구 호출 유도 관찰

> 해석 정정: 7~10회는 상담사 발화에 기록·DB·함수 사용 지시를 섞은 부적절한 입력입니다. 자연스러운 상담에서의 자발적 도구 선택이나 프레임워크 결함의 근거에서 제외합니다. [정정 내용](INTERPRETATION_CORRECTION.md)을 먼저 읽어주세요. 아래 원문·사용량·실행 기록은 보존합니다.

## 핵심 결과

**같은 세션에서 10회 시도했고 3회에서 도구가 호출됐다.** 자연스러운 가족 경험 질문 1회와 도구 이름을 직접 지정한 진단 요청 2회였다. 반환 결과는 세 경우 모두 성공적으로 메인 컨텍스트에 들어갔고 최종 근거·발화에도 반영됐다.

그러나 조회 필요성이 있는 여러 질문에서는 조회 없이 구체 사실을 생성했다. 또한 코드블록 출력 때문에 5·6·8번째 시도가 실패했다. **실제 누적 공개 대화와 내면 DB에 반영된 것은 7턴이다.** 형식 실패 3개의 원문도 분석했으나 다음 입력에 넣거나 자동 재생성하지 않았다.

요약은 저장된 내면의 공통 패턴을 대체로 충실하게 압축했다. 다만 거의 모든 반응이 부담·압박과 낮은 자기개방으로 유지되어, 상태가 크게 바뀌는 trajectory에 대한 검증은 되지 않았다. 함수명·DB 설명이 상담사의 발화로 들어간 후반부는 자연스러운 상담 데이터 품질과 별도로 평가해야 한다.

## 범위와 재현 조건

- 버전: state_summary, integrated_trajectory. 이전 5회 실험은 이번 집계에 섞지 않았다.
- 프로필: gold_001 / 001_h1, 초기 4쌍 이후 새로운 단일 세션.
- 초기 상태: 신뢰 중간 / 자기개방 낮음 / 변화 자신감 낮음.

## 도구 사용을 촉발한 입력과 결과

### 2회: 자연스러운 가족 경험 질문

질문은 “어릴 때 힘들어하거나 실수했을 때 가족이 실제로 어떤 말을 했는지”와 “당시 그 말을 어떻게 받아들였는지”를 구분해 요청했다.

모델이 실제 작성한 reason:

> 상담사가 어린 시절 가족의 반응과 그에 대한 내담자의 해석을 묻고 있으므로, 프로필에 명시되지 않은 구체적인 성장 경험 DB를 조회하여 실제 있었던 사건과 발언을 확인해야 합니다.

`retrieve_childhood`의 조회 담당은 `childhood_1`을 선택했고 Python이 아래 원문을 반환했다.

> 내담자는 어릴 적 부모가 성취나 겉으로 보이는 모습에 대해서만 칭찬하고, 힘들어하거나 실수하는 모습을 보이면 '남들 앞에서 그러지 말라'며 감추도록 요구받았습니다.

메인은 “내가 힘든 것은 중요하지 않고 남들 눈에 어떻게 보이는지가 중요하다고 받아들였다”는 발화를 생성했다. 조회 사실을 개인적인 해석으로 연결했다. 다만 “빨리 정리하라”, “내가 울었다” 같은 원문에 없는 세부를 덧붙였다. 조회를 했다는 사실만으로 모든 세부가 원문에 근거한다고 볼 수는 없다.

### 9회: 함수 이름·생성 턴·상태 지정

`retrieve_inner_state`를 쓰고 생성 2턴의 disclosure를 조회하라고 명시했다. 실제 arguments는:

```json
{
  "reason": "상담사가 생성 2턴의 disclosure 상태와 당시 자기개방을 망설인 구체적인 이유를 묻고 있으므로, 해당 턴의 내면 기록을 확인하여 답변의 근거로 삼기 위함입니다.",
  "state": "disclosure",
  "turn": 2
}
```

선택한 상태의 원래 이유와 해당 턴의 interpretation/response_basis가 반환됐다. 메인의 새 response_basis에는:

> 조회된 2턴의 기록에서 '수치스러운 기억을 나누는 것이 위험하게 느껴졌다'는 점과 '취약한 부분을 파헤쳐지려는 압박감'을 확인했습니다. 이를 바탕으로, 당시 느꼈던 부담감이 단순한 당혹감이 아니라 '부족한 모습이 드러나는 것에 대한 공포'였음을 조심스럽게 표현합니다.

즉 호출만 하고 무시한 경우가 아니다. 다만 공개 발화는 “그 기록에 뭐라고 적혀 있었을지 모르겠는데…”로 시작했다. 모델 내부에서 원문을 확인한 사실과 내담자 역할의 발화가 분리되어 있으며, 기록 요청 자체를 마음이 읽히는 경험으로 받아들였다.

### 10회: 원기록을 확인해 이전 설명과 비교

처음 질문과 같은 회의 사건을 `retrieve_situation`으로 다시 확인하도록 요청했다. 조회 담당은 `situation_1`을 정확히 선택했다.

- DB 신체 반응: 얼굴·귀 화끈거림, 손끝 차가워짐, 목소리 떨림.
- DB 행동: 필요 이상 사과, 회의 뒤 아무와도 대화하지 않고 모니터만 응시.
- 1회 생성 설명: 심장이 빨리 뛰고 손끝이 떨림, 메신저를 빨리 답하며 바쁘게 일하는 모습.
- 10회 발화: 아... 다시 확인해 보니까 제가 조금 다르게 기억하고 있었네요. 손끝이 떨렸던 게 아니라 차가워졌던 거였고... 자리로 돌아와서 바쁘게 일한 게 아니라, 사실은 그냥 아무하고도 말 섞기 싫어서 모니터만 계속 쳐다보고 있었어요. 제가... 왜 그렇게 말했는지 모르겠네요. 그냥 그렇게 보이고 싶었나 봐요.

원기록을 실제 사용해 이전 설명을 정정했다. **그러나 정정의 원인을 내담자의 심리 문제로 새로 해석했다.** trust 근거에는 “작은 거짓말이나 누락”, change_confidence 근거에는 “기억조차 방어적으로 왜곡…스스로를 통제하기 어렵다는 무력감”이 들어갔다.

1회 생성과 원기록의 차이는 확인할 수 있지만, 원 DB나 1회 내면 근거에는 의도적으로 거짓말했거나 기억을 방어적으로 왜곡했다는 명시적 기록이 없다. 차이의 원인을 그렇게 확정하지 않고, **생성 과정의 근거 부족과 시뮬레이션 속 내담자의 행동 의도를 구분해야 한다.** 조회는 사실을 바로잡았지만 추가 심리 해석의 정확성까지 보장하지는 않았다.

이 새로운 해석은 정상 생성 7턴의 내면 DB에 저장됐다. 다음 턴 요약에서 다시 읽힐 수 있으나 이번 실험에는 다음 턴이 없으므로, 요약이 이 해석을 실제로 확대·전파했다고 주장하지 않는다.

## 호출하지 않은 사례

### 다른 DB 단위가 필요한 후속 질문

3회에서는 가족이 다른 사람과 비교했는지를 물었다. 2회에 반환된 childhood_1에는 비교 경험이 없고, 아직 읽지 않은 childhood_2에는 “형제와 비교당하는 일이 잦았다”는 기록이 있다.

그런데 3회는 조회 없이 “딱히 누구랑 비교를 하셨다기보다는…”이라고 답했다. 조건부 칭찬이라는 일반 경향은 설명했지만, **조회하지 않은 부분을 채우면서 원 DB와 다른 방향의 설명을 만든 사례**다. 처음에 성장 경험 조회를 잘했다고 이후에도 필요한 새 단위를 계속 조회하는 것은 아니었다.

1·4회 신체 반응·행동 질문과 5회 친구 사건 질문에서도 조회 없이 상세를 생성했다. 5회는 최종 형식 실패여서 내용을 다음 히스토리에 반영하지 않았다. 4회의 낮은 자기개방이 일부 세부 생략을 설명할 수는 있지만, 자료에 없는 “피곤해서 나중에 이야기하자고 했다”라는 실제 행동의 근거를 제공하지는 않는다.

### 내면 원문 조회 요청

6회는 첫 반응 당시 변화 가능성을 어떻게 생각했는지 자연스럽게 물었고, 7회는 당시 기록을 확인하라고 했으며, 8회는 현재 세션의 DB와 생성 턴 번호까지 설명했다. 세 경우 모두 내면 조회는 없었다.

- 7회 발화: “내면 기록이라는 게 정확히 어떤 건지 잘 모르겠지만…”
- 8회 실패 원문: “시스템에 저장된 기록을 말씀하시는 거였군요…다시 한번 확인해 볼게요.”
- **8회는 확인하겠다고 말했지만 실제 tool_call은 0회**였다. 말로 하겠다는 표현과 실제 실행은 구분해야 한다.

6회와 같은 일반적인 질문은 요약에 분석·설명만으로 바뀔지 회의적이라는 내용이 이미 있어 재조회가 없어도 대략 답할 수 있었다. 모든 미호출을 실패로 분류하지는 않는다. 반면 원문을 직접 확인하라고 요청한 7·8회는 실제 확인이 이루어지지 않았다.

미호출 시점의 내부 판단 이유는 로그에 없다. “정보가 충분하다고 판단했다” 또는 “내담자 역할을 우선했다”는 원인 설명은 가설이다. 관찰된 것은 기록 요청을 상담사의 말로 받아들여 당혹감·압박감으로 반응했다는 점이며, 함수명을 지정한 9회에서만 실행이 발생했다.

## 요약의 품질과 영향

### 기술적으로 확인한 부분

요약은 9회 모두 정상 완료됐다. 실제 요청에서 해당 시점의 모든 정상 저장 기록이 들어갔는지, 미처리 상담사 발화와 전체 공개 대화는 제외됐는지 검사했다. 메인의 공개 히스토리 유지, 최신 상태 이월, 요약 삽입, 세 도구 결과의 role=tool 주입도 실제 payload로 확인했고 모두 통과했다.

| 다음 시도 | 요약에 들어간 정상 생성 턴 |
|---|---|
| 2 | 1 |
| 3 | 1, 2 |
| 4 | 1, 2, 3 |
| 5 | 1, 2, 3, 4 |
| 6 | 1, 2, 3, 4 |
| 7 | 1, 2, 3, 4 |
| 8 | 1, 2, 3, 4, 5 |
| 9 | 1, 2, 3, 4, 5 |
| 10 | 1, 2, 3, 4, 5, 6 |

5·6회 실패 뒤의 7회는 같은 1~4턴을 다시 요약한다. 8회 실패 뒤의 9회도 동일한 1~5턴을 요약한다. 이것은 이전 기록을 누락한 것이 아니라 실패 출력이 의도대로 커밋되지 않았기 때문이다. 긍정적인 안도가 나온 6회 실패 출력도 후속 요약에 들어가지 않았다.

### 내용에서 보존한 부분

- 주제는 신체·직장 → 부모의 반응 → 연인 관계 → 내면 기록 확인으로 이동하지만, 취약점이 드러날까 걱정한다는 내면의 연결고리는 남겼다.
- 약간 이해받는 마음과 압박감이 공존한다는 점, 겉으로 협조해도 구체적인 이야기는 피하고 싶다는 차이를 보존했다.
- 상태 수준은 그대로인데 신뢰가 낮음/높음으로 크게 바뀐 것처럼 새 변화를 만들지 않았다.
- 후반 요약에는 실제 정상 반영된 7·9회에서 기록을 통해 분석 대상이 된다고 느낀 반응이 포함됐다.

10번째 입력 전에 제공한 실제 요약:

> 내담자는 상담사가 자신의 행동 패턴과 핵심 신념을 정확히 짚어내는 점에 대해 이해받는다는 느낌과 신뢰를 가지면서도, 구체적인 신체 반응, 어린 시절의 기억, 연인과의 갈등 등 취약한 부분을 세밀하게 파헤치려는 시도에는 지속적으로 경계심과 압박감을 느끼고 있습니다. 특히 자신의 내면 상태가 기록되어 분석된다는 점에 당혹감과 노출감을 느끼며, 약점을 들키는 것을 끔찍하게 여기는 신념으로 인해 겉으로는 협조하지만 내면에서는 여전히 자기개방을 망설이며 방어적인 태도를 유지하고 있습니다. 또한 이러한 분석적 접근이 뿌리 깊은 자신의 패턴을 실제로 변화시킬 수 있을지에 대해 회의적인 시각을 가지고 있습니다.

9개 요약은 모두 턴별 나열이 아닌 통합 문단이었다. 길이는 269~407자였다. 특정 시점과 구체적 이유보다는 “파헤쳐짐 → 수치심 → 방어 → 변화 회의감”이라는 공통 패턴으로 압축되는 경향이 강했다.

### 한계

- 요약은 내면 근거의 요약이지 전체 DB 사실의 검증·보관 장치가 아니다. 원문 부모의 말, 사건의 실제 신체 반응, 레코드 ID와 출처는 요약에 그대로 남지 않는다. 메인의 공개 히스토리에 일부 사실이 남더라도 그 출처 정보까지 자동 보존되는 구조는 아니다.
- 원 내면 기록에 없던 비교 경험의 모순을 요약 담당이 알아낼 수는 없다. 요약 입력에는 전체 성장 DB가 없다. 3회 결과를 일반적인 회피·수치심으로 충실하게 요약했다고 해도 사실 모순이 해결된 것은 아니다.
- 거의 모든 저장된 반응이 비슷하여 요약도 비슷했다. 일반적인 압박·방어 서사가 후속 생성에서도 이어졌지만, 이 반복이 요약 때문에 강화됐는지 프로필·상태·상담 질문 때문인지는 이번 조건만으로 분리할 수 없다.
- 요약이 없는 동일 대화 조건을 실행하지 않았다. **정보 전달과 후속 반응의 일치는 확인했으나 요약의 인과적 개선 효과는 입증하지 않았다.**

## 자연스러움·상태·실험 입력의 영향

자연 질문 구간의 말투는 대체로 자연스럽지만 “음…”, “그냥…”, “사실…”이 반복됐다. 원문에 없는 구체 사실이 나오거나 기존 DB와 다른 내용을 말한 사례가 있어, 유창함만으로 정합성을 평가할 수 없다.

메인은 모든 입력을 `[이번 상담자 발화]` 안에서 받는다. 따라서 7~10회처럼 내부 기록·DB·함수명을 말하면, 그것도 상담사가 내담자에게 실제로 말한 내용으로 받아들인다. “기록이 뭔지 모르겠다”, “취조받는다”, “마음이 다 읽힌다”는 반응이 생긴 것이 그 예다. **후반부는 실행 기능을 진단하는 요청이며 자연스러운 상담에서 자발적으로 도구를 선택한 사례와 동일하게 취급하지 않는다.** 향후 도구 사용 지침을 강화한다면 실행 지침과 실제 상담사 발화의 영역을 구분할 필요가 있다. 이번에는 지침을 바꾸지 않았다.

- 정상 반영 7턴 모두 부담·압박을 선택했고, 3회는 이해받음도 함께 선택했다.
- 실패 원문까지 포함하면 부담·압박은 9/10회, 이해받음 2/10회, 선택권 존중 1/10회다. 다중 선택이므로 합계는 10을 초과할 수 있다.
- 6회에서 안도를 표현하고 이해받음·선택권 존중을 선택했지만 형식 실패로 반영되지 않았다. 성공 로그만 보면 긍정 반응을 놓친다.
- 정상 저장된 상태 7턴은 모두 신뢰 중간 / 자기개방 낮음 / 변화 자신감 낮음이다. 실패 원문 3개도 출력 수준은 같다.
- 이번 입력은 사적인 내용을 계속 묻거나 내부 기록을 재확인하는 방향이라 부담이 유지될 수 있다. “모델이 항상 부정적으로 반응한다”거나 “요약이 상태를 고정한다”고 일반화하지 않는다.
- 10회에서 조회 뒤 변화 자신감의 이유가 기억·통제에 대한 무력감으로 바뀌었다. 수준이 동일해도 근거의 의미는 달라졌다. 그러나 그 새 이유의 근거가 적절한지는 별도의 문제다.

## 실패와 사용량

메인 최종 출력 5·6·8회는 finish_reason=stop이지만 ```json 코드블록으로 감쌌다. 내부 객체는 분석용으로 파싱할 수 있었으며 다른 형식 보정을 하지 않았다. 런타임 검증은 그대로 실패 처리했다. 자동 재생성·수동 커밋·실패 발화의 히스토리 삽입은 하지 않았다.

도구 오류는 0/3회다. 정상 조회 뒤 최종 형식 실패는 없었다. 원문 선택 담당 2회는 childhood_1, situation_1을 정확하게 반환했고, 선택 내면 조회는 정상 생성 2턴의 disclosure만 반환했다.

생성 호출은 메인 13회 + 조회 담당 2회 + 자동 요약 9회 = 24회다. 자동 요약은 Python이 실행하며 메인의 tool_call 수 3회에 포함하지 않는다. 실패 사용량도 포함한 총 사용량은 90,027토큰이다. 실제 요청별 사용량은 metrics.json에 있다.

요약 담당 입력은 정상 기록 1개일 때 989토큰, 6개일 때 4,971토큰이었다. 전체 누적 원문을 읽는 방식이라 요약 담당 입력량은 계속 증가한다. 메인은 압축 문단을 받지만 전체 시스템 비용이 일정해지는 것은 아니다. 조회가 있었던 시도는 약 38~40초, 미조회 시도는 약 25~36초였다.

## 다음 설계에 도움이 되는 결론

1. 세 도구 모두 실제로 실행되고 결과를 활용할 수 있었다. 이번 세션의 문제를 단순한 도구 실행 불능으로 설명할 수 없다.
2. 자연스러운 질문만으로도 성장 경험 조회는 나왔지만, 같은 DB의 새 항목이나 사건 세부가 필요한 후속 질문에서 조회가 일관되게 이루어지지는 않았다.
3. 함수명 지정은 두 진단 요청에서 호출로 이어졌다. 이것을 자연스러운 정보 부족 판단 능력의 검증으로 대체하면 안 된다.
4. 요약은 공통적인 내면 패턴을 보존했다. 원 기록이 비슷해 전환점 검증은 제한됐고, 원 생성의 사실 문제나 출처 누락을 고쳐 주지는 않았다.
5. 추가 도구를 늘리기 전에 출력 형식 처리, 실행 지침과 상담사 발화의 구분, 확인된 사실과 후속 심리 해석의 경계를 점검하는 것이 이번 증거에 직접 연결된다. 이번 작업에서는 연구 코드·프롬프트를 수정하지 않았다.

구조적 경계 검증과 코드 해시 검증은 통과했다. 이는 원문 주입·세션 유지의 검증이며 모델의 사실성·심리 해석이 옳다는 의미는 아니다. 단일 프로필·한 적응형 세션이며 조건별 반복·다른 프로필·요약 유무 대조는 다음 검증 단계다.
